# Jev Test Auditor — Technical Design

## Decision

Build one TypeScript CLI with a framework-neutral domain, Jest/Vitest/bun:test evidence adapters, a TypeSafe Jev gateway, append-only SQLite persistence, and deterministic JSON/HTML reporting. The system scans only tests; production source is supporting evidence.

## Architecture

```text
CLI
 └─ Audit application
     ├─ Repository discovery
     ├─ Jest/Vitest/bun:test test-case extraction
     ├─ Context resolver
     ├─ Evaluation scheduler ── TypeSafe Jev
     ├─ Classification policy
     ├─ SQLite run store and cache
     └─ JSON report ── self-contained HTML renderer

Benchmark application
 ├─ Git-versioned fixture/operator catalog
 ├─ Executable deterministic oracles
 ├─ Same evaluation scheduler and policy
 ├─ SQLite history, comparisons, and JSONL export
 └─ Optional project skill ── lightweight runtime subagents
```

Dependencies point inward: CLI and renderers depend on application services; application services depend on domain contracts; repository, Jev, SQLite, and filesystem concerns implement ports.

## Core domain

| Type | Responsibility |
| --- | --- |
| `TestCase` | Stable identity, file/line/name, framework, source, helpers, imports, and test kind. |
| `EvidenceBundle` | Minimal test, helper, production-seam, and provenance fragments sent for judgment. |
| `RubricVersion` | Seven dimension definitions, criteria, questions, and composition policy. |
| `DimensionJudgment` | Applicability probability, 0–3 score distribution, confidence, and model metadata. |
| `Finding` | Test-bound concern with evidence and derived status. |
| `AuditRun` | Immutable configuration, progress, usage, failures, and report identity. |

Identifiers use normalized repository-relative paths plus structural test ancestry and a source hash. Line numbers are presentation metadata, not identity.

## Discovery, extraction, and the Phase 2 audit seam

1. Discover repository-local `.test`/`.spec` JavaScript, JSX, TypeScript, and TSX files with lexical ordering, default/configured exclusions, symlink containment, and conservative E2E signals.
2. Read source through a root-contained filesystem adapter. Discovery and reading inspect text only; they never execute audited files, package scripts, test runners, or configuration modules.
3. Attribute Jest/Vitest/bun:test from syntax-aware static imports (and, for bun:test, `require`) and package metadata (Jest/Vitest only — bun is a runtime, not an npm dependency, so it has no package.json evidence source). Conflicting evidence remains `unknown` and is preserved in the discovery record.
4. Parse JavaScript, JSX, TypeScript, and TSX with the TypeScript compiler API.
5. Extract `describe`, `test`, `it`, parameterized variants, modifiers, hooks, imports, mocks, and assertion calls.
6. Emit one `TestCase` per statically identifiable case. Dynamic cases that cannot be enumerated receive explicit extraction metadata rather than invented identities. A file whose framework cannot be attributed (including conflicting evidence) and that yields zero test cases emits one `unsupported-framework` warning diagnostic naming the test-framework-looking imports actually found (e.g. `node:test`), or stating plainly that none were found — never a silent empty result, and never a warning for a recognized framework's genuinely empty file. `bun:test` is a fully supported framework (not merely recognized evidence): it attributes `bun` and extracts suites, cases, modifiers (including bun-only `test.serial`, preserved as its own kind with no Jest/Vitest equivalent, and `.if`/`.failing` mapped onto the existing `runIf`/`fails` kinds), hooks, mocks (`mock`, `spyOn`, `mock.module`, and the re-exported `jest` object — recorded under a `bun.`-prefixed `MockApi` so bun provenance is never mistaken for real Jest), assertions, and static parameter tables exactly like Jest/Vitest. Deliberately deferred: `*_test.*`/`*_spec.*` filename patterns and the `.mjs`/`.cjs`/`.mts`/`.cts` extensions bun also recognizes — discovery's existing `.test`/`.spec` JS/JSX/TS/TSX pattern is unchanged.
7. The application service composes discovery, safe source reading, and extraction through injected ports. It processes included files sequentially in repository-relative lexical order and returns per-file lineage, exclusions, root diagnostics, and `reportingOnly: true`. For a file discovery attributed `unknown` (step 3 found no import/package evidence — e.g. an ambient-global Jest spec, which never imports `@jest/globals`), it additionally consults the optional `jestFrameworkHint` port (`src/adapters/jest-project-config.ts`), which reads — never executes — the nearest ancestor `package.json`'s `jest` key, a `"test": "jest"`-style script, or a `jest.config.*` file's presence, deliberately walking past `rootDir` itself to find that ancestor (bounded by the first `package.json` found or a `.git` boundary). This is consulted purely as a fallback: it feeds `extractTestCases`'s existing `frameworkHint` parameter, whose own precedence (a file's own imports always win; more than one imported framework stays `unknown` outright) is unchanged, and it never fires when conflicting project evidence (a Vitest dependency/script/config file) is present. The corrected framework is reflected back onto that file's `AuditFileResult.discovered.framework` (what both the CLI summary and `audit --json` print); `discovered.frameworkEvidence` itself is unaffected, since `FrameworkEvidenceSource` has no `'config'` member.

`jev-test-auditor audit` projects this result — plus the same no-network, no-write cost/call estimate `--dry-run` computes (`estimateDryRun`, reused verbatim; see "Dry-run cost and call estimate" below) — into one human-readable report, ordered so a reader gets the run's shape before the detail behind it: the configured `rootDir`; the discovery totals (including `unsupportedFrameworkFiles`, the count of files carrying an `unsupported-framework` diagnostic) together with the cost estimate; then the evidence-provenance detail those numbers rest on (fragments, omitted, denied, unresolved); then the listings; then diagnostics. Included files are summarized by path, framework, and count, truncated past 20 entries with a count of what was left out and a pointer to `--json`. Exclusions are reported as counts grouped by reason, and only the reasons that could mean an expected test was skipped over — `configured-exclude`, `default-exclude`, `e2e-v1`, `symlink`, `outside-root`, and a test-named file excluded solely by a non-default include pattern — are additionally listed path by path. `not-test-file` and `unsupported-extension` fire once per ordinary file in the tree, so they dominate volume while telling a reader nothing; they are counted, never enumerated, and whenever anything is collapsed the report says so and points at `--json` for the complete list. The bundle count is deliberately not restated: one evidence bundle is built per test case, so it duplicates `Discovered test cases`, and the only case where the two diverge is already surfaced more specifically as an `evidence-unavailable` skip and its own diagnostic. `audit --json` prints the underlying discovery data alone as one deterministic JSON line (`rootDir`, per-file summaries, excluded paths/reasons, totals, diagnostics) instead — the same shape `audit` has always exposed, now reached only through this flag rather than by default. Parser, read, and discovery diagnostics are informational for CLI policy: `audit` exits zero after emitting the report; usage errors exit one.

Skipped and todo cases remain visible but are not silently treated as evaluated active tests. E2E framework files are excluded in v1.

## Context resolution

Evidence resolution and selection are hand-rolled and auditable: they never use `require.resolve`, `createRequire`, or Node module resolution, and they never import, require, or execute an audited file, helper, configuration module, package script, or test runner.

**Resolution (per file, once).** A relative specifier (`.`/`..`/`./`/`../`) resolves lexically against its importer's directory. A non-relative specifier is first checked against the importing file's own statically declared alias mapping table (`src/adapters/alias-config.ts`, built per nearest configuration and cached per directory for the run) before it is ever classified `bare-specifier`/`alias-specifier`.

**Alias mapping table.** Three mechanisms are read, each read as text/JSONC and never executed:

- Node subpath `imports` (`package.json`, `#name`/`#name/*` keys only), from the **nearest** `package.json`. A conditional value resolves `default`, then `import`, then `node`; any other condition is recorded (`imports-unsupported-conditions`) rather than guessed.
- TypeScript/JavaScript `paths` and `baseUrl` (`tsconfig.json`/`jsconfig.json` `compilerOptions`), from the **nearest** tsconfig/jsconfig (`tsconfig.json` preferred over `jsconfig.json` at the same directory level), following in-root `extends` chains left to right for an array — child settings override the parent's wholesale, never merged key-by-key, matching TypeScript's own behavior. `paths` targets resolve relative to the effective `baseUrl`'s directory when a `baseUrl` exists anywhere in the chain (TypeScript's own rule, regardless of which config in the chain textually declared `paths`), or relative to the directory of whichever config declared `paths` when no `baseUrl` exists at all. An `extends` target outside the repository root, or resolving into `node_modules` (including an npm-published base config such as `@tsconfig/node20/tsconfig.json`), is refused and recorded (`extends-outside-root`/`extends-node-modules`), never followed; a cycle is caught by an ancestry stack of realpaths and recorded (`extends-cycle`) rather than recursed into. `baseUrl` alone (no `paths`) also acts as a bare `*` catch-all — a search root rather than a declared mapping, so a `baseUrl`-only config never sets `alias-mapped-not-found` for an unmatched specifier, and `lodash`/`@nestjs/core` etc. still fall back to `bare-specifier`.
- Workspace package names, read once from the **root** `package.json`'s `workspaces` globs and each member package's own `package.json` `name` — root-only, unlike the other two mechanisms, which use the nearest config to the importing file. A bare package name's targets are tried `packageDir/src/index` (through the normal probing rules), then the package directory's own top-level probing, then the package's declared `exports['.']`/`main` entry (source-preference rule) — so a package whose entry is generated `dist` output resolves to source when source exists, and is reported `denied` (never silently dropped) only when it does not; a `name/*` subpath maps directly to `dir/*`, without consulting `exports` subpaths other than `.`.

**Matching and precedence.** Precedence across mechanisms: `imports` → `paths` → `workspace` → `baseUrl` — the first mechanism with a matching entry is used. Within one mechanism, TypeScript's own `matchPatternOrExact` rule applies: an exact (star-less) pattern equal to the specifier wins outright over any wildcard, regardless of declaration order; otherwise, among matching wildcard patterns, the one with the longest prefix (the text before its single `*`) wins, ties broken by declaration order; a pattern containing two or more `*` characters never matches anything. A matched entry's targets are tried in declaration order (with the workspace source-preference reorder applied only to a bare, non-wildcard workspace name entry); the wildcard's captured text is re-checked for containment after substitution into each target, because the declared target string was already checked at config-read time but the specifier's own captured portion is caller-controlled and could contain `../` segments. The first target that produces an existing file — `resolved`, `denied`, or an escaping-symlink/unsupported-extension outcome — is terminal for that specifier: resolution does not fall through to try a *later* mechanism, even if a lower-precedence mechanism would have resolved differently. This is a deliberate divergence from a literal "first mechanism that produces an existing, in-root, non-denied file wins" reading; it was verified empirically inert on the three repositories measured for this phase (no case where a denied/out-of-root target's specifier also had a viable match elsewhere), but is not proven correct in general. A target producing no candidate at all is not terminal: the search continues to the next target, then the next mechanism. A specifier matched by a declared `imports`/`paths`/workspace entry whose every target was missing is `alias-mapped-not-found`, distinguishing a stale mapping from a specifier no mechanism recognized (which still falls back to `bare-specifier`/`alias-specifier` below). A hop-2 helper file's specifiers are resolved against the **helper's own** nearest configuration, never the test file's.

Every resolved target — mapped or relative — is still probed through the exact same extension/index order, the same deny-before-extension-check gate, and the same realpath containment check as before this phase; alias matching is a layer in front of that machinery, which is otherwise unchanged.

A specifier starting with `@/`, `~/`, or `#` that matched no mapping is classified `alias-specifier`; every other non-relative specifier that matched no mapping — including a scoped package such as `@babel/core` — is `bare-specifier`. Both are recorded as `unresolved` with that reason; neither is ever read. For a relative specifier, or an alias-mapped target, candidates are probed in this exact order: the literal path; then, only when the base's own extension has a TS-ESM rewrite (`.js`→`.ts`/`.tsx`, `.jsx`→`.tsx`, `.mjs`→`.mts`, `.cjs`→`.cts`), the rewritten path(s); then, unless the base already has a recognized source extension, the base with each of `.ts`, `.tsx`, `.js`, `.jsx`, `.mts`, `.cts`, `.mjs`, `.cjs` appended; then, always, the base as a directory with `index<ext>` for each of those extensions. The first candidate that exists, stays within the repository root after `realpath` (rejecting a symlink escape), and is a regular file wins. **Deny is checked before any extension-support check and before the file is ever opened**: a repository-relative candidate matching a deny pattern is reported `denied` with the matching rule, never `unresolved` — denial always wins over "this extension isn't supported." Deny patterns without a `/` match the candidate's basename at any depth (e.g. `*.pem` denies `secrets/key.pem`); patterns with a `/` match the full path with the same glob semantics as repository discovery's excludes. Configured `deny` patterns are additive to `DEFAULT_EVIDENCE_DENY_PATTERNS`, never a replacement.

**Import depth (the helper hop).** Hop 1 is the test file's own imports (relative and alias-mapped alike). A hop-1 file is classified `helper` when it is itself a test file, sits under a `test`, `tests`, `__tests__`, or `__mocks__` path segment, or has `helper`, `fixture`, or `setup` in its basename (case-insensitive); everything else is `production`. Only `helper` files are expanded one further hop (hop 2, their own imports, resolved with the same rules against the helper's own nearest configuration); production files and every hop-2 file are terminal — never expanded further, regardless of role.

**Selection (per test case).** For the test body plus every in-scope hook, referenced import bindings (named, aliased, default, namespace, and `require(...)` destructures) are resolved to the smallest top-level declaration exporting that name in the target file — a whole function/class declaration, a whole `const`/`let`/`var` statement, or `export default`; a name only re-exported from elsewhere selects the re-export statement itself, never following into the next file. A module statically registered as a mock (`jest.mock`/`vi.mock`/`doMock`) reclassifies its otherwise `helper`/`production-seam` fragment as `mock-target`. Selection priority, highest first: the test body and its hooks (`test`), then hop-1 imports (`helper`/`production-seam`/`mock-target`), then hop-2 imports reached only through a hop-1 helper's own selected declaration text (not its whole file).

**Budgets, truncation, and omission.** Each fragment is capped at a configurable `maxFragmentBytes` (default 4 KiB); a fragment that overflows is truncated at the last full line that fits, falling back to a raw UTF-8-safe byte cut (never splitting a multi-byte character) only when not even one line fits. The whole bundle is capped at `maxBundleBytes` (default 16 KiB): fragments are added in priority order until one would overflow, that one fragment is truncated to the remaining budget (line-boundary only; no byte-cut fallback at this stage), and every fragment after it is recorded as `omitted` with a reason rather than silently dropped. Budgets are provisional pending later calibration.

**Canonical form.** Every fragment records repository-relative path, span, a SHA-256 content hash of its newline-normalized text, selection reason, and truncation state (`truncated`, `originalBytes`, `includedBytes`). `canonicalizeEvidenceBundle` serializes a bundle to one deterministic JSON string — fixed key order, fragments/denied/unresolved/omitted sorted independently of input order, paths normalized, content newline-normalized — so identical inputs always produce byte-identical output (what a later phase's cache hashes). `--inspect-payloads` prints exactly this canonical form, one JSON line per bundle, after the normal summary line: it is the local evidence state actually selected on disk, not the Jev wire request shape (`buildJevState`/`buildJevRequest`, below), and it involves no network call — enforced by a static check that `src/` never imports a raw network module and never calls a bare `fetch(...)` outside the one reviewed call site in the TypeSafe gateway adapter, alongside a runtime check that stubs `fetch` during a real audit run.

## Dry-run estimation

`src/domain/estimate.ts` is a pure domain module (no Node imports) that turns an already-built audit result into an aggregate cost/call preview, driven by a versioned, injectable `JevEstimateSnapshot` (its canonical definition now lives in `src/domain/jev-pricing.ts` — see "Module layering" below — and is re-exported from `estimate.ts` unchanged) and an injectable `Rubric` (defaulting to `RUBRIC_V2`, matching what a real `--evaluate` run uses since `odd/tasks/classification-calibration.md` task C-2; it defaulted to `RUBRIC_V1` before that task). `JEV_ESTIMATE_SNAPSHOT` is the shipped instance: the exact pinned model `JEV_MODEL_ID` (`jev-1.13.0`, reused by identity rather than a re-typed literal so the estimator can never drift from the rubric's pin), USD 0.042 per 1,000,000 input tokens, output tokens unbilled, a 3.0–4.8 bytes-per-token range, one follow-up per test at most, a 64k-token provider request ceiling, `asOf: '2026-09-20'`. `validateJevEstimateSnapshot` rejects a non-positive/non-finite/inverted-range snapshot deterministically with `RangeError`, checked before any file is read; an invalid injected `rubric` is likewise rejected (via `buildJevQuestions`'s own `validateRubric` call) before any file is read. `JEV_VERIFIED_RATE_LIMITS`, recorded alongside the snapshot, documents the verified provider rate limits (250,000 input tokens/second, 1,200 requests/minute, 2026-09-20) as facts only — nothing in this phase reads or enforces them.

**Corrected from a real measurement (2026-09-20).** The first real Jev run (11 requests, small fixture) measured 71,855 billed input tokens. The estimator's previous method — an evidence-bundle byte count plus a guessed `requestOverheadTokens` range (620–2,440 tokens) standing in for the rubric's cost — produced 12,747–37,523 tokens for that same run: the estimate did not even contain the true value. The real rubric text (`RUBRIC_V1`'s 14 questions) costs ~26,979 canonical bytes per request, about 93% of the ~29,124-byte average real request, dwarfing the guessed overhead. The fix: since the rubric is in the repository, `estimateDryRun` now builds the real request per evaluable test case (`buildJevRequest`) and measures its exact canonical bytes (`canonicalizeJevRequest`) instead of guessing. `requestOverheadTokens` is deleted from `JevEstimateSnapshot`; `bytesPerToken` is re-calibrated around the observed 4.458 bytes/token ratio (320,360 measured request bytes / 71,855 billed tokens), and the snapshot's `version` bumped to `2` to mark the methodology change.

**Bounds are asymmetric on purpose, not a symmetric margin around the sample.** `bytesPerToken` is `{ min: 3.0, max: 4.8 }`, not a tight band around 4.458. The two bounds fail in different directions: a real ratio above `max` (content tokenizes more efficiently) makes `estimatedInputTokens.min` an overestimate — annoying, harmless. A real ratio below `min` (content tokenizes less efficiently — denser JSON, non-Latin/CJK source whose UTF-8 multibyte characters often cost a full token each) makes `estimatedInputTokens.max` an underestimate — the reported range would not even contain the true billed cost, which is the exact failure this whole correction exists to fix. `min` is therefore set deliberately conservative (well below the single observed sample) rather than tight around it; `max` stays closer to the sample since overestimating is the safe direction. This rests on ONE real run of 11 English/TypeScript requests — a repository whose evidence is mostly non-Latin source could still tokenize below 3.0, a known current limit until more varied real runs are measured.

**Classification (`classifyTestCase`).** Every extracted test case is `skipped/skip` or `skipped/todo` when it carries that static modifier (checked first, so a skip/todo test with no built bundle still reports its modifier reason, never `evidence-unavailable`); `skipped/evidence-unavailable` when no modifier applies but evidence selection produced no bundle for it; `evaluable` otherwise — including a `skipIf`/`runIf` conditional modifier, which is a runtime condition rather than a statically known skip.

**Exact quantities.** `discovered` and `skipped`-by-reason counts come directly from that classification. `initialCalls` equals `evaluable` (one Jev request per evaluable test case, matching the "one state, all rubric questions batched" evaluation model). `evidenceBytes` is the exact sum of `canonicalizeEvidenceBundle(bundle)` UTF-8 byte lengths over every evaluable bundle — the same canonical form `--inspect-payloads` prints, so a byte-for-byte cross-check between the two flags is possible (and is exercised by the packed-install smoke test) — kept for its own sake, but no longer what the token/cost math is derived from. `requestBytes` is the exact sum of `canonicalizeJevRequest(buildJevRequest({ testCase, bundle, rubric }))` UTF-8 byte lengths over every evaluable test case: the actual request Jev would receive. `rubricBytesPerRequest` is the exact UTF-8 byte length of just the rubric's own canonical `questions` map (`canonicalizeJevRequestQuestions(buildJevQuestions(rubric))`) — the same for every evaluable request under a given rubric, independent of test-case count, computed even when `evaluable` is `0` (it depends only on the rubric) — reported so a reader can see how much of a request's cost the rubric itself accounts for.

**Approximate ranges, explicitly labeled.** Each evaluable test case's own `requestBytes` converts to a token range by dividing by `bytesPerToken.{max,min}` and rounding outward (`floor` for the `min` bound, `ceil` for the `max` bound), so the reported range never under-covers the value it approximates, and the per-test-case ranges sum into `estimatedInputTokens`. `followUpCalls` is `{ min: 0, max: evaluable * maxFollowUpsPerTest }` — exact bounds on an inherently unknown count, since a follow-up only happens when an earlier result identifies a specific evidence need, never an automatic retry. Because a follow-up re-sends the same state, `estimatedFollowUpInputTokens.max` is `estimatedInputTokens.max * maxFollowUpsPerTest` (worst case: every evaluable test uses its full follow-up budget) and `.min` is `0` (best case: none do). `estimatedUsd` prices `estimatedInputTokens.min` (no follow-ups) through `estimatedInputTokens.max + estimatedFollowUpInputTokens.max` (every possible follow-up) at `usdPerMillionInputTokens`; Jev's output tokens are unbilled, so no output-token term is ever added. `bundlesOverCeiling` counts evaluable test cases whose own real request's worst-case tokens (`ceil(requestBytes / bytesPerToken.min)`) would exceed `requestTokenCeiling` — a coarse whole-request check (expected `0` under the current evidence budgets); the provider's finer 32k state-plus-longest-question sub-limit still needs per-question text and stays `checkJevRequestBudget`'s concern (`src/domain/jev-request.ts`), which this dry-run estimator does not duplicate.

**Module layering (avoiding an import cycle).** `estimateDryRun` needs `buildJevRequest`/`canonicalizeJevRequest` from `src/domain/jev-request.ts` to measure a real request's bytes — but `jev-request.ts` also needs `estimateTokensFromBytes` and `JEV_ESTIMATE_SNAPSHOT.bytesPerToken` (for its own `JEV_REQUEST_LIMITS`, read at module load time) from the estimator's pricing snapshot. Defining both directions in the same two files would make `estimate.ts` and `jev-request.ts` import each other — a real ES module cycle, not just awkward layering: depending on which module a consumer imports first, the cyclic partner can read the other's `const` before it initializes (a TDZ `ReferenceError`), which the `type: "module"`/`NodeNext` setup here does not paper over. The pricing snapshot and the pure `estimateTokensFromBytes` conversion (plus the `DryRunRange` type it returns) now live in their own module, `src/domain/jev-pricing.ts`, with no dependency on `jev-request.ts`, keeping the module graph a DAG: `jev-pricing.ts` → `jev-request.ts` → `estimate.ts`. `estimate.ts` re-exports every pricing name unchanged, so this split is invisible to `src/index.ts`, `src/cli/index.ts`, and existing tests.

**CLI.** `audit --dry-run` runs the identical no-network, no-write discovery/extraction/evidence pipeline as a normal audit, then prints a concise human-readable report — just this estimate, nothing about discovered/excluded files or diagnostics (now including `Request bytes` and `Rubric bytes per request` lines alongside `Evidence bytes`); `--dry-run --json` prints the same data as one stable-key-order JSON line, with `requestBytes` and `rubricBytesPerRequest` fields alongside `evidenceBytes`. The plain `audit` default folds this identical estimate (via the same `costEstimatePreambleLines`/`costEstimateBodyLines` `src/cli/index.ts` lines `dryRunTextReport` itself uses) into its own broader report; `audit --json` prints the underlying discovery data alone, unaffected. `--dry-run` combined with `--inspect-payloads` or `--evaluate`, and `--evaluate` combined with `--inspect-payloads`, are usage errors (exit 1) — detailed bundle rendering stays exclusive to `--inspect-payloads`; diagnostics from the underlying audit never change `--dry-run`'s exit code. `--json` alone is no longer a usage error (previously: `--json` without `--dry-run`/`--evaluate`). `audit --evaluate` (below) sends this exact same request `state`/`questions` and reports exact usage from the provider's own response — `--dry-run`'s token/cost figures stay an approximation of that exact usage, converted from the same exact bytes.

**Delivered (Phase 5, task P5-5): cache-hit and billable-call accuracy.** `estimateDryRun` gained a fourth, optional parameter, `cacheHitTestCaseIds?: ReadonlySet<TestCaseId>` — plain data, never a port or a filesystem read, keeping this function a pure domain function with no I/O. When supplied, a test case whose id is in the set is excluded from `initialCalls`/`followUpCalls`/`estimatedInputTokens`/`estimatedFollowUpInputTokens`/`estimatedUsd` and counted instead in a `cacheHits` field; `evaluable`/`evidenceBytes`/`requestBytes`/`rubricBytesPerRequest`/`bundlesOverCeiling` stay scoped to every evaluable test case regardless, since they describe the discovered work itself, not what would be billed for it. `cacheHits` is present (even as `0`) only when the cache was actually consulted (see below).

**Delivered (orchestrator decision, 2026-09-20): explicit cache-consultation disclosure.** P5-5 itself flagged two decision gaps rather than resolving them unilaterally (`odd/tasks/phase-5-persistence.md`, "Open questions carried forward"): whether a cold dry run should stay byte-identical to before P5-5 or plainly disclose "no cache was consulted" (the task text asked for both, which conflict for the cold case read literally), and whether `openSqliteAuditStoreForLookup`'s "older schema degrades silently, newer/corrupt throws" split was the right discrimination. Both resolve the same way: **disclose explicitly, in a new field, rather than only through a missing key.**

`estimateDryRun` gained a fifth, optional parameter, `cacheNotConsultedReason?: DryRunCacheNotConsultedReason` (`'no-store' | 'schema-outdated'`, `src/domain/estimate.ts`) — plain data, ignored whenever a hit set was actually supplied. `DryRunEstimate` gained two fields: `cacheConsulted: boolean`, **always present** (unlike `cacheHits`), so a JSON consumer never has to infer "consulted, zero hits" from a missing key; and `cacheNotConsultedReason?: DryRunCacheNotConsultedReason`, present only when `cacheConsulted` is `false` and a reason is known. `dryRunJsonLine` spreads `cacheConsulted` in immediately after `initialCalls`, then `cacheHits` or `cacheNotConsultedReason` (mutually exclusive, matching `cacheConsulted`) — this **is** the one deliberate, disclosed change to the previously byte-for-byte-identical cold `--dry-run --json` shape; the existing golden fixture test (`test/cli.test.ts`) was updated to the new exact string rather than loosened to a substring match, per this task's own instruction. `dryRunTextReport` adds no new line when the cache WAS consulted (the existing `Cache hits` line already covers that case, unchanged) — only a `Cache: not consulted (...)` line, naming the reason, when it was not.

`openSqliteAuditStoreForLookup` itself now returns a discriminated union, `AuditStoreLookupResult` (`{ available: true; lookup } | { available: false; reason }`), instead of `AuditStoreReadOnlyLookup | undefined` — the one function that already knows *why* a lookup is unavailable is also the one function that reports it, so the CLI only ever passes `reason` straight through to `estimateDryRun` with no re-derivation that could drift. The schema-version discrimination itself is unchanged (see below): a version newer than this build, or corrupt/foreign, still throws the same named, visible error a real `--evaluate` would also raise — confirmed correct, not silently loosened, by resolving both decision gaps as "disclose more," never "fail less."

Refactoring `openSqliteAuditStoreForLookup`'s return shape from a loose `| undefined` to a checked discriminated union exposed a pre-existing self-deceiving test in `test/sqlite-audit-store.test.ts`: a test asserting "a row sitting only in an uncheckpointed WAL sidecar is invisible to the reader" used `lookup?.lookup(...)` — with `lookup` itself potentially `undefined` for an unrelated reason (the store's own schema, also only in the WAL, was invisible too) — so the assertion `expect(hit).toBeUndefined()` passed regardless of which case actually occurred, the same "vacuous by construction" pattern this phase has repeatedly warned about. Fixed by checkpointing the schema in a separate bootstrap-and-close step before the real, never-closed write, isolating the row-visibility question the test actually claims to prove.

The CLI computes the set with a new application-layer function, `computeDryRunCacheHits` (`src/application/audit.ts`): for every currently evaluable test case (reusing the same private `collectEvaluableItems` helper `runEvaluation` itself uses), it computes the real cache key through the caller-supplied `AuditCacheKeyPort` and looks it up through a caller-supplied `lookup` function — the identical two calls a real dispatch makes before evaluating. Calling the exact same functions with the exact same inputs, rather than independently re-deriving an equivalent key, is what guarantees a dry run's billable count agrees with what a subsequent real `--evaluate` run over the same fixture and store actually dispatches, by construction rather than by careful duplication that could drift.

Reaching each evaluable test case's real cache key needs its whole file's raw source text — the one ingredient `AuditFileResult` never carries (see the P5-2 note above on why not). `runAudit` gained `RunAuditOptions.retainSourceText?: boolean` (default `false`): when `true`, the per-file `sourceTextByPath` map `runAudit` already builds internally when `ports.evaluation` is present (for its own cache-key lookups) is built regardless, and exposed on `AuditResult.sourceTextByPath`. An ordinary audit, and even `--evaluate` without this option explicitly set, sees no new field on its result — the exposure is opt-in on top of an already opt-in internal map, not merely "is the map non-empty."

**The read-only, no-write guarantee.** `--dry-run` "may read an existing store, but must never create one, never migrate one, and never write anything" (`odd/tasks/phase-5-persistence.md`, task P5-5) — the same append-only posture the store already has for `--evaluate`, tightened to no writes at all here. `openSqliteAuditStoreForLookup` (`src/adapters/sqlite-audit-store.ts`) is the one function that owns this:

- `stat`s the resolved database file first and returns `{ available: false, reason: 'no-store' }` immediately if it does not exist — the one case the task names explicitly ("no store exists yet"); this never loads `node:sqlite` at all (no `ExperimentalWarning`, no native open attempt against a path that is not there).
- Otherwise opens it through a `file:` URI — built with `pathToFileURL`, never raw string concatenation (a `#`/`?`/`%` in the resolved path, e.g. inside `XDG_CONFIG_HOME`, would otherwise corrupt a hand-built URI, confirmed empirically on this project's own dev machine) — carrying `immutable=1`, plus `{ readOnly: true }` as a second, independent guard. `immutable=1` is the load-bearing piece, verified empirically rather than assumed from documentation, both ways: `readOnly: true` alone still makes SQLite create `-shm`/`-wal` sidecar files for a WAL-mode database on its first `SELECT` (it needs the wal-index to read a consistent snapshot); `immutable=1` alone (no `readOnly` option at all) already refused a write outright ("attempt to write a readonly database") and created no sidecar, since it tells SQLite the file will not change and skips that locking/indexing machinery entirely. `readOnly: true` is kept anyway as `node:sqlite`-level defense-in-depth, not because it is independently necessary. Confirmed to create no sidecar file and leave the main file byte-identical (hash and size), both against a cleanly closed store and one still holding an uncheckpointed `-wal` file from a live connection that never closed.
- **Known, documented limitation of `immutable=1`**: a row sitting only in an uncheckpointed `-wal` sidecar is invisible to this reader, which reads only the main file's own last-checkpointed content — confirmed empirically (a row written but never checkpointed does not appear through the immutable connection, while the same row is visible once the writer closes cleanly). This can only ever make a dry run *under*-report cache hits, never the reverse, and never affects the ordinary case this task's own tests verify: sequential CLI invocations, each of which closes its store connection cleanly (`runCli`'s own `finally`), so everything is already checkpointed by the time a later invocation opens the file.
- **Schema compatibility, decided by "what would a subsequent real `--evaluate` against this exact file do?"**, never a separate policy: a version newer than this build's `SCHEMA_VERSION`, or a store `readSchemaVersion` already rejects as corrupt/foreign (a malformed `schema_meta` row, or user tables with no `schema_meta` at all), throws the identical named error (`AuditStoreSchemaVersionError`/`AuditStoreCorruptError`) a writable `--evaluate` open of the same file would also throw — reused unchanged by the CLI's existing catch (readable message, exit 1, no stack trace) — rather than silently reporting a happy "N billable" preview a real run could never actually produce. A version *older* than this build (no `cache_key` column can exist yet, so no hit is possible) degrades to `{ available: false, reason: 'schema-outdated' }` ("not consulted") instead of failing, because a subsequent real `--evaluate` would simply migrate it forward first and then dispatch every evaluable test case — the same outcome "not consulted" already reports, and (orchestrator decision, 2026-09-20, see above) the exact reason `estimateDryRun`/the CLI report to the user.
- The live store's own `lookup` and this read-only reader's `lookup` share one module-level SQL constant (`LOOKUP_CACHED_JUDGMENT_SQL`) rather than two hand-copied query strings, so the two can never silently drift on what counts as a hit.

**CLI wiring**, gated exactly like `--evaluate`'s own store construction (never for the `dependencies.audit` test seam, and only for `--dry-run` itself): `runCli` opens the read-only lookup before running the pipeline, passes `retainSourceText: true` to `runAudit` only when a store was actually found (so the common cold path pays no extra memory for retaining source text it will never use), computes the cache-hit set after the pipeline runs, and closes the read-only handle in the same `finally` that already closes the writable `--evaluate` store. When `openSqliteAuditStoreForLookup` reports `{ available: false, reason }`, that `reason` is threaded straight into `estimateDryRun`'s fifth parameter unmodified — the CLI never re-derives or re-interprets it, so the adapter's own discrimination and the report's own disclosure can never silently disagree.

## Jev evaluation

One request represents one `TestCase` state, built by `buildJevState`/`buildJevRequest` (`src/domain/jev-request.ts`) from a `TestCase` and its `EvidenceBundle`: identity, structural ancestry, framework, modifiers, fragments (path, kind, selection reason, truncation, content — never hashes, spans, or byte counts, which carry no judgment-relevant meaning), and denied/unresolved/omitted provenance so the model can tell "withheld from me" from "does not exist." Independent questions share that state and are batched — 14 total, two per each of the rubric's seven dimensions (`RUBRIC_V2`, `src/domain/rubric.ts` — `RUBRIC_V1` is the original Phase 4 wording, kept only to replay evidence recorded against it; task C-2 of `odd/tasks/classification-calibration.md` rewrote `RUBRIC_V2`'s `determinism-isolation`/`falsifiability` applicability questions to ask whether the shown evidence supports a judgment, rather than whether every possible influence is visible):

- A `noul` applicability question asking whether the supplied state is sufficient to judge that dimension at all.
- A `score` quality question with four ordered levels: misleading, weak, acceptable, strong.

A dimension is excluded from the overall verdict outright, as `not-applicable`, when its applicability `noul` is below the policy's `applicabilityMin` (0.5); once applicable, the shipped `CLASSIFICATION_POLICY_V2` decides its level from the quality answer's probability distribution rather than from `confidence` — see "Classification policy" below. Follow-up requests remain out of scope for this phase; a dimension lacking sufficient evidence stays `needs-review` rather than triggering a second call.

The shipped rubric (`RUBRIC_V2`) pins the exact model id `JEV_MODEL_ID` (`jev-1.13.0`); every request carries this pin, and the response's own `model` is recorded and compared (`modelMatchesPin`) — a mismatch is always reported in the classification result, never hidden or silently retried. Raw answers (`JevEvaluation.answers`, with each answer's own `raw` field) remain stored on the normalized evaluation result so a policy change can be recomputed without another model call when question meaning and evidence are unchanged. The gateway (`src/adapters/jev-http-gateway.ts`) is a hand-rolled `fetch` client behind the `JevGatewayPort` domain port: `Authorization: Bearer` auth from `TYPESAFE_API_KEY` (validated eagerly at construction, so it is constructed only when evaluation is actually requested), a 60s timeout, bounded retry (3 retries, full-jitter exponential backoff, 500ms initial/30s cap) for 429/529 only honoring `retry-after`, and typed errors for every other failure. The API key is never accepted as a constructor argument on any thrown error type, and every server- or transport-derived string is redacted before it can reach an error message — the key cannot leak into a log, report, or diagnostic by construction, not by best-effort scrubbing.

**Opt-in wiring (`audit --evaluate`).** `src/adapters/jev-evaluation-port.ts` composes `buildJevRequest` + a `JevGatewayPort` + `classifyEvaluation` into the domain-typed `AuditEvaluationPort` (`src/domain/audit.ts`). `runAudit` (`src/application/audit.ts`) evaluates every evaluable test case — reusing `classifyTestCase` from `src/domain/estimate.ts` so "evaluable" is never redefined — if and only if `AuditPorts.evaluation` is present; when absent, evaluation is skipped entirely and nothing constructs a gateway or reads an API key. Evaluation runs through a fixed-size concurrency pool sized from `configuration.concurrency` (no adaptive throttling this phase), writing each result to its own index so ordering stays deterministic regardless of completion order. A rejected `evaluate` call is isolated to its own test case: it contributes no classification (never a fabricated verdict, never counted healthy) and produces one `evaluation-failed` diagnostic naming the test case id and the error's typed kind, merged into both that file's own diagnostics and the run's root diagnostics. The CLI (`src/cli/index.ts`) prints a terminal evaluation summary (status counts, skipped-by-reason, failed, total usage input tokens, responded model id, model-mismatch count, and a full diagnostics block) for `--evaluate`, or one deterministic canonical JSON line for `--evaluate --json` carrying every classification's dimensions, findings, model requested/responded/matchesPin, usage, policy/rubric versions, and per-test evidence provenance counts (fragment/truncation/denied/unresolved/omitted counts, looked up from that test case's bundle).

**Local API key storage (Phase 4, task P4-5).** `--evaluate` resolves its key through `resolveApiKey` (`src/domain/auth.ts`, pure): `TYPESAFE_API_KEY` first (non-blank), else the locally stored per-user file, else a usage error naming both `auth login` and the environment variable. Storage (`src/adapters/auth-storage.ts`) resolves a platform-appropriate path (`$XDG_CONFIG_HOME`/`~/.config`/`%APPDATA%` plus `jev-test-auditor/credentials.json`) and writes `{ version: 1, apiKey }` through a temp-file-plus-`rename` sequence with the mode (`0o700` directory, `0o600` file) set at creation — never write-then-`chmod`, which would leave a window where the file is world-readable. Reading refuses (fail closed) a file whose POSIX permissions are more permissive than owner-only; Windows does not enforce this and says so. Every filesystem operation and the platform-detection environment are injectable, so tests never touch the real per-user config directory. The interactive prompt (`src/adapters/auth-prompt.ts`) hides input on a real TTY (raw mode, no echo, Ctrl+C cancels and always restores the terminal) and reads one trimmed line otherwise, so piped/CI input works without a terminal. `auth status` never reads the stored file's content when an environment key is already available, and never prints the key or any part of it.

## Classification policy

Classification (`src/domain/classification.ts`) is deterministic, pure, and non-compensatory. Each dimension is judged independently by `judgeDimension`, which dispatches structurally (`isClassificationPolicyV2`) to `judgeDimensionV1` or `judgeDimensionV2` depending on which policy shape it receives. The shipped port (`src/adapters/jev-evaluation-port.ts`) always constructs `CLASSIFICATION_POLICY_V2` paired with `RUBRIC_V2`; nothing in this codebase constructs a `CLASSIFICATION_POLICY_V1` or requests `RUBRIC_V1` any more. Both are kept exported, unchanged, and still fully tested only because the 2026-09-20 discrimination-fixture recording (`test/fixtures/recorded/discrimination-raw-2026-09-20.json`) is real provider output captured against that exact rubric wording, and `test/classification-replay.test.ts` needs `RUBRIC_V1`/`CLASSIFICATION_POLICY_V1` to keep existing in order to recompute it.

Applicability is unchanged by task C-1 (`odd/tasks/classification-calibration.md`): a missing or wrong-shaped applicability answer forces `needs-review`; `applicabilityProbability` below `applicabilityMin` (0.5 in both policy versions) excludes the dimension outright as `not-applicable`, and its score is never recorded. Task C-2 changes what the applicability *question itself* asks for `determinism-isolation` and `falsifiability` (see "Rubric v2 applicability rewrite" below), not this gate.

Once a dimension is applicable, `judgeDimensionV2` replaces `judgeDimensionV1`'s `confidence`-gated cut-point comparison with a decision read directly from the quality answer's four-level `probabilities` distribution:

- `deficientMass = P(misleading) + P(weak)`, `acceptableMass = P(acceptable) + P(strong)`, `criticalMass = P(misleading)`.
- The dimension is **deficient** when `deficientMass >= sideMin` (0.65) and **acceptable** when `acceptableMass >= sideMin`; because `sideMin` must exceed 0.5, these are mutually exclusive. Neither side clearing `sideMin` reports `needs-review`, reason `boundary-straddle` — the verdict only ever depends on this one deficient-vs-acceptable boundary, so probability spread between two levels on the *same* side no longer produces `needs-review`.
- A deficient dimension reports **misleading** only when `criticalMass >= criticalMin` (0.5); otherwise **weak** — a merely-deficient distribution can never read as a critical accusation.
- An acceptable dimension still distinguishes `acceptable` from `strong` for reporting, using the old score-based cut point (`levelCutPoints[2]`, `score >= 3`, via `levelForScore`) — that distinction can never itself produce `needs-review`.
- `score` and `confidence` are still recorded on every judgment (`DimensionJudgment.score`/`.confidence`), and `probabilities`/`deficientMass`/`acceptableMass`/`criticalMass` are exposed alongside them in the JSON report (task C-1's "expose per-level probabilities" requirement) — but none of them gate the level or the verdict any more; they are transparency, not policy. A dimension's reported `score` can therefore fall inside a nominally weaker cut-point band (e.g. 1.97, under the `weak`/`acceptable` cut point of 2) while its `level` reads `acceptable`, because the mass — not the weighted mean — decided it; see "Measured results" below for a real recorded example.

The overall verdict (`classifyOverall`) is unchanged by task C-1 and remains non-compensatory by construction: any judged `criticalLevel` (`misleading`) dimension forces the whole verdict to `misleading` before anything else is inspected, so no `strong`/`acceptable` dimension anywhere can cancel it; any judged `weak` dimension (with no critical failure) forces `weak`; a model-pin mismatch, zero applicable dimensions, or any remaining `needs-review` applicable dimension forces `needs-review`; `healthy` requires every applicable dimension to be judged `acceptable` or `strong`.

`CLASSIFICATION_POLICY_V2`'s `applicabilityMin` (0.5), `sideMin` (0.65), and `criticalMin` (0.5) are provisional, versioned thresholds, not calibrated claims — picked mid-gap from the ranges actually observed in the 2026-09-20 discrimination-fixture recording (full derivation in `src/domain/classification.ts`'s module and constant doc comments). A later benchmark phase (Phase 7) calibrates them against ground truth; recalibration is a new policy version (e.g. `CLASSIFICATION_POLICY_V3`), never a silent edit of a shipped constant.

### Rubric v2 applicability rewrite

Task C-2 rewrites only the `determinism-isolation` and `falsifiability` applicability questions in `RUBRIC_V2` (`src/domain/rubric.ts`); every other dimension's text, every quality question, every label, and every question id are inherited byte-for-byte from `RUBRIC_V1` (asserted directly by `test/rubric.test.ts`). The rewrite was needed because both v1 questions asked, in effect, "is every possible influence on this dimension visible?" — a question the evidence bundles evaluation actually sends are deliberately built to answer "no" to, since a bundle carries only the test's own body plus a minimal helper/production-seam slice, never the whole repository. Measured on the 2026-09-20 discrimination fixture, this made `determinism-isolation` read as not-applicable (below the 0.5 threshold) on 7 of the 11 tests — including the one deliberately written to violate determinism with `Math.random()` and module-level shared state — and made `falsifiability` read as not-applicable on 4 of the 11, several of them just under the 0.5 cut, including a healthy control that asserts an exact value. `RUBRIC_V2`'s rewrite asks instead whether the shown evidence — the test's own body, and any in-scope hook fragment — supports a judgment at all: absence of a visible hazard is itself evidence of determinism, not a reason to abstain. Both rewrites keep a concrete inapplicable criterion (no evidence shown at all), so a genuinely evidence-starved test still abstains rather than becoming unconditionally applicable. `CLASSIFICATION_POLICY_V2.rubricVersion` is pinned to `2`; `classifyEvaluation` fails closed (`RangeError`) on any policy/rubric version mismatch.

No number in this section is a calibrated-accuracy claim, and none of `CLASSIFICATION_POLICY_V2`'s thresholds are validated by it — they remain provisional, versioned guesses.

## Persistence and cache

**Delivered (Phase 5, task P5-1).** `audit --evaluate` persists every terminal work-item outcome to a local, per-user SQLite database through `AuditStorePort` (`src/domain/audit.ts`), implemented by the `node:sqlite` adapter `src/adapters/sqlite-audit-store.ts`. Schema version 1 uses migrations (idempotent on re-open, transactional) to create seven tables, now at schema version 3 after Phase 6, task P6-1 (see below):

| Table | Contents |
| --- | --- |
| `runs` | One row per audit run: `id`, `root_dir`, `started_at`, `finished_at`. |
| `work_items` | One row per work-item checkpoint reached, referencing its run; `state` is `CHECK`-constrained to the full seven-value `WORK_ITEM_STATES` enum. P5-1 wrote only the terminal `completed`/`failed`/`skipped`; P5-2 added `cached`; P5-3 adds the two non-terminal checkpoints `pending` (recorded for every evaluable item up front, before the scheduler dispatches anything) and `running` (recorded the moment the scheduler picks that item up) — see "Scheduling and recovery" below. A work item can therefore have several rows over its lifetime (append-only: `pending` → `running` → a terminal state), never one updated in place. A schema version 2 migration (P5-2) adds a nullable `cache_key` column, indexed, populated on `completed` and `cached` rows only — never on `pending`/`running`. |
| `attempts` | One row per completed work item: requested/responded model, whether the response matched the pin, attempt count, raw answers (JSON), and input/output token usage. Never written for a `cached` row — no provider request was made, so there is no attempt to record. A schema version 3 migration (P6-1) adds two nullable columns: `latency_ms` (the whole `evaluate()` call's wall-clock milliseconds, including every internal retry and backoff wait) and `attempt_latencies_ms` (a JSON array, one wall-clock duration per HTTP attempt actually made — never including a backoff wait). Both are nullable for the identical reason `cache_key` is: a row written before this migration ran never captured latency at all, and the migration never fabricates a value for it. |
| `judgments` | One row per completed OR cached work item: status, policy/rubric versions, and the full classification (JSON). A cache hit gets its own append-only judgment row, a duplicate of the reused classification, never a reference back to the original. |
| `errors` | One row per failed work item: error kind and message. |
| `skips` | One row per skipped work item: the skip reason. |
| `schema_meta` | One row (`id = 1`) recording the store's current `schema_version`. |

**Why an explicit `schema_meta` table, not `PRAGMA user_version`.** `PRAGMA user_version` is a raw integer any SQLite database can already be using for its own purposes; a foreign database that happens to set that pragma for something unrelated could be misread as an audit store already at some schema version, and adopted or migrated incorrectly. An explicit `schema_meta` table with this adapter's own row shape is unambiguous: its absence on a database that already holds other tables means "not ours," never "version 0" — a genuinely empty database (no tables at all) still migrates normally.

**Two named failure types**, both exported from `src/domain/audit.ts`, so no raw native error ever escapes to a caller:

- `AuditStoreSchemaVersionError` — the store's recorded `schema_version` is *newer* than this build's supported `SCHEMA_VERSION`. Never migrated backwards, never silently recreated.
- `AuditStoreCorruptError` — every other way the store cannot be opened safely: a missing or malformed `schema_meta` row (absent row, or a `schema_version` that is not a non-negative integer); a database that already holds user tables but no `schema_meta` table at all — a foreign database, refused rather than silently adopted; and any native `node:sqlite` driver failure wrapped by `wrapNativeSqliteError` — a file that is not a SQLite database, a directory in place of the file, or a read-only file.

**`node:sqlite` is loaded through a dynamic import inside a narrow suppression window**, not a static `import { DatabaseSync } from 'node:sqlite'`. A static import evaluates the module — and emits its one-time `ExperimentalWarning` ("SQLite is an experimental feature and might change at any time") — before the adapter's own code has run at all, so nothing in this module could ever wrap or suppress it. `withSqliteExperimentalWarningSuppressed` instead wraps `process.emitWarning` only for the duration of `import('node:sqlite')`, filtering out exactly the sqlite experimental-feature warning shape (`isSqliteExperimentalWarning`); every other warning — including a *different* `ExperimentalWarning` — still reaches the user unchanged, by construction rather than by convention. A shared patch and depth counter, not a naive per-call save/restore, keep this correct under overlapping concurrent calls to `createSqliteAuditStore`.

**`AuditEvaluationPort.evaluate` returns both the raw evaluation and the derived classification** (`{ evaluation, classification }`, widened from Phase 4's classification-only result), because the store persists raw answers (`attempts.raw_answers`) as records distinct from normalized judgments (`judgments.classification`) — recomputing a policy without another Jev call needs the raw answers kept, not only the final verdict.

**`finishRun` is the adapter's only row mutation** — it sets a run's own `finished_at` column exactly once, when that run completes. This does not violate the append-only guarantee: a run is a single logical fact ("this run happened, and finished at time T"), completed once; no method here ever updates or deletes a previously written run, work item, attempt, judgment, error, or skip record.

**Delivered (Phase 5, task P5-2): the content-addressed cache key, lookup, and `--fresh`.** `AuditCacheKeyPort` (`src/domain/audit.ts`), implemented by `src/adapters/cache-key.ts`, computes `sha256` over a JSON payload combining:

- `canonicalizeJevRequest`'s existing deterministic serialization of the real `{ state, model, questions }` request (`src/domain/jev-request.ts`) — this **already covers**, with no separate hash input needed, the pinned model id (`request.model`, i.e. `rubric.model`) and every rubric question's wording (`request.questions`), plus the evidence bundle's selected fragments/denied/unresolved/omitted entries (`request.state.fragments` etc.);
- the normalized full test-file source hash — **not** already covered, since `state.fragments` carries only what evidence selection actually chose (the test body span, in-scope hooks, referenced helpers/production seams), never the whole file, so an edit elsewhere in the file would otherwise go undetected;
- the rubric's own numeric `version` — **not** already covered, never embedded in `state`/`model`/`questions` anywhere (today a rubric bump also rewrites question wording, so the canonical request bytes already differ too, but the explicit version field is the decision for a hypothetical future bump whose wording stays unchanged);
- the classification policy's own numeric `version` — **not** already covered, never sent to Jev at all (the policy runs entirely locally, after the fact, against the raw answers already returned).

`hashEvidenceBundle` (`src/adapters/evidence-hash.ts`, reserved for exactly this since Phase 4) is deliberately **not** used: `canonicalizeEvidenceBundle`'s serialization additionally includes each fragment's `span`, `contentHash`, and byte counts, which would over-invalidate the key on a pure line shift with unchanged fragment content — `state.fragments` (already inside the canonical request) deliberately excludes exactly those fields.

The key never depends on `rootDir`: `canonicalizeJevRequest`'s paths are already repository-relative (Phase 3 provenance), proven by a test that computes the same key from two different absolute roots over identical repository content.

`runEvaluation` (`src/application/audit.ts`) looks up each evaluable item's key through `AuditStorePort.lookup` before dispatching, when a cache-key port and a store are both present (opt-in exactly like evaluation and storage themselves, and always wired together by the CLI's `createProductionPorts` — never one without the other). A hit records a `cached` work item and reuses the stored judgment, at zero token cost; a miss (or `--fresh`) dispatches exactly as before and records `completed` with the computed key, so a later run can find it. `--fresh` bypasses the lookup only — it never skips recording, so its result is still a new, immutable, appended `completed` record.

**Lookup rule, several results per key.** Append-only plus `--fresh` means one key can accumulate more than one `completed` judgment. `AuditStorePort.lookup` returns the most recent (`work_items.id DESC`, never `recorded_at`, a millisecond-resolution string that can collide) `completed` work item under that key whose attempt's `model_matches_pin` is `1`; a pin-mismatched row is skipped in favor of an older matching one, and no matching row at all is a miss. Only `completed` rows are ever eligible — a `cached` work item's own judgment is never itself a lookup source, so every hit traces back to exactly one real provider response. A `completed` row recorded with no `cache_key` (a caller that never wires the cache-key port) can never be a hit, since the comparison never matches a stored `NULL`.

**The `uncertain` work-item state remains undefined.** Nothing in this codebase produces it as of P5-2; the schema's `CHECK` constraint and `WORK_ITEM_STATES` admit it purely for forward compatibility. A later phase that wants to produce it must define what it means before doing so.

**Reporting.** `AuditEvaluationTotals` (`src/domain/audit.ts`) gains a `cached` count alongside `evaluated`. Both count toward `statusCounts`/`respondedModel`/`modelMismatches` identically (a cached judgment is a valid, already-computed verdict), but only `evaluated`'s tokens are folded into `usage.inputTokens`/`outputTokens` — a cache hit's classification carries the *original* evaluation's usage, and counting it again would overstate what the current run actually spent. The CLI's `--evaluate` text and `--json` reports surface `Cached`/`cached` next to `Evaluated`/`evaluated`.

**Delivered (Phase 5, task P5-5): cache-aware `--dry-run`.** `audit --dry-run`'s `initialCalls` now counts only billable test cases — one not already served by an existing store's content-addressed cache — with cache hits reported separately (`cacheHits`). See "Dry-run estimation" above for the full design: the pure-domain `estimateDryRun` signature change, the new `computeDryRunCacheHits`/`RunAuditOptions.retainSourceText` application-layer plumbing, and — the central engineering problem this task solved — `openSqliteAuditStoreForLookup`'s read-only, no-write, no-migrate guarantee (a `file:` URI carrying `immutable=1`, verified empirically to create no sidecar file and leave the store byte-identical).

**Delivered (orchestrator decision, 2026-09-20): explicit cache-consultation disclosure.** Resolves both decision gaps P5-5 itself flagged (see "Dry-run estimation" above for the full design): `DryRunEstimate.cacheConsulted` is always present, and `cacheNotConsultedReason` (`'no-store'` | `'schema-outdated'`) names why whenever it is `false` and a reason is known — a cold dry run's report is no longer byte-identical to before P5-5 (that byte-identity was the exact tension the task text raised), it now plainly discloses "not consulted" and why, which the orchestrator judged the correct resolution of that stated conflict.

**Delivered (Phase 6, task P6-1): per-request latency capture and the schema version 3 migration.** The gateway (`src/adapters/jev-http-gateway.ts`) now measures wall-clock latency around `evaluate()`'s whole call — including every internal retry and the backoff wait between attempts — and, separately, around each individual `attemptOnce` call (the request and reading its whole response body, never a backoff wait). Both are threaded onto the normalized result as `JevEvaluation.latencyMs` (whole-call total) and `JevEvaluation.attemptLatenciesMs` (one entry per HTTP attempt made, in order) — see that type's own doc (`src/domain/jev-gateway.ts`) for why the two numbers matter together: a genuinely slow provider (one long attempt) reads differently from one that answered fast every time but was retried after a 429/529 (several short attempts, a long total because of the backoff waits in between). Measurement uses the gateway's existing injectable clock (`CreateJevHttpGatewayOptions.now`, the same seam `parseRetryAfterMs` already used) rather than a new seam — deterministic in tests, and never a new pattern alongside P5-3's separate `SchedulerClock`/`SchedulerSleep` (`src/application/scheduler.ts`), which times the application-layer scheduler, not the gateway's own HTTP calls. Neither number changes the gateway's timeout, abort, or 429/529 backoff behavior (purely additive instrumentation around unchanged control flow), and neither is used as a throttle signal — P5-3's signal stays exactly `attempts > 1` on success or a typed `rate-limit`/`overloaded` error kind, never a wall-clock heuristic (a wall-clock signal was explicitly rejected in Phase 5's own decisions).

Persisted by a schema version 3 migration on `attempts` (`latency_ms`, `attempt_latencies_ms` — see the table above), transactional and idempotent like every migration before it; a hand-built schema version 2 fixture upgrades to version 3 without losing a row (`test/sqlite-audit-store.test.ts`), and a store at an unknown or newer version still fails with `AuditStoreSchemaVersionError`. `openSqliteAuditStoreForLookup`'s existing version check (`version < SCHEMA_VERSION` degrades to `{ available: false, reason: 'schema-outdated' }`) already covers a v2 store read by v3 code with no change needed: a `--dry-run` against a pre-P6-1 store degrades to "not consulted" exactly like every other older-schema store, never migrating.

Both new fields are optional on `JevEvaluation`: always present for a live gateway call, but omitted (never a fabricated `0` or `[]`) for a `JevEvaluation` reconstructed from a completed work item recorded before this migration existed. Latency is threaded through `AuditEvaluationOutcome.evaluation` (`src/domain/audit.ts`) and is visible to the application layer wherever the whole evaluation already flows — `runEvaluation`'s success branch (`src/application/audit.ts`) and the persisted `AuditStoreWorkItemOutcome.completed.evaluation` — exactly like `usage`/`attempts` already are. It is deliberately **not** threaded onto `ClassificationResult` or into the existing `--evaluate --json` CLI output (`evaluateJsonLine`, `src/cli/index.ts`): surfacing latency in a report is Phase 6, task P6-2's job, which decides how the canonical JSON report exposes it (most likely reading it from the same `evaluation` object this task already carries, or from a resumed run's `attempts` columns) — P6-1 only measures, threads, and persists it.

Further out, and equally unbuilt: report manifests (Phase 6, "HTML reporting", see "Reports" below) and the benchmark-history tables — fixture operators, oracle proofs, benchmark runs, metrics, comparisons, and their JSONL export (Phase 7, "Benchmarks and calibration", see "Deterministic evaluation" and "Benchmark agent-review skill" below). Schema version 3 has no tables for any of this yet.

## Scheduling and recovery

**Delivered (Phase 5, task P5-3): adaptive concurrency and request/token budgets.** Evaluation no longer runs through Phase 4's fixed-size `runBoundedPool`. `src/application/audit.ts`'s `runEvaluation` now dispatches through `runAdaptiveSchedule` (`src/application/scheduler.ts`), a dynamic-concurrency dispatcher driven by `createAdaptiveConcurrencyController` (`src/domain/scheduler.ts`, pure — no I/O, no timers). The controller starts at `concurrency` (the configured ceiling, never exceeded), halves the effective limit (floored, never below 1) on an observed provider throttle, and restores it by one step after `DEFAULT_ADAPTIVE_CONCURRENCY_RESTORE_WINDOW` (5) consecutive clean dispatches — a named constant, not user-configurable, chosen conservatively so one lucky success does not walk straight back into the same 429/529 that triggered the reduction. The gateway's own per-call timeout, abort, and 429/529 backoff (`src/adapters/jev-http-gateway.ts`) is untouched: the scheduler wraps the outer dispatch loop, never the gateway's internal retry.

**Throttle-signal derivation is decision, not detection.** The gateway retries 429/529 internally and returns only the final outcome, so `runEvaluation` never observes a 429 directly. Rather than widen the gateway's contract, it reuses two seams that already cross the port boundary: a successful evaluation's own `JevEvaluation.attempts` (already persisted as `attempts.attempts`) is greater than 1 only because the gateway retries exclusively on 429/529, so `attempts > 1` on a success is exact evidence the provider pushed back before eventually letting the request through; a failed evaluation's typed error kind of `'rate-limit'` or `'overloaded'` (`JevRateLimitError`/`JevOverloadedError`) is throttling that was never recovered from. Every other outcome — a cache hit (no provider request was made at all) or any other failure kind (auth, malformed response, timeout, abort) — reports `'neutral'`: it changes the concurrency limit in neither direction and neither advances nor resets the clean-window streak, so an unrelated failure storm cannot masquerade as either "the provider is throttling us" or "traffic is clean."

**Request/token budgets are observed, not merely documented.** `ResolvedConfiguration.schedule` (`src/domain/config.ts`) resolves `requestsPerMinute`/`tokensPerSecond`, defaulting to `JEV_VERIFIED_RATE_LIMITS` (1,200 requests/minute, 250,000 tokens/second — the same verified facts Phase 4 recorded but never enforced), overridable by a library consumer exactly like `store.databasePath` (no CLI flag). `createRequestTokenBudgetGate` (`src/application/scheduler.ts`) tracks two independent rolling windows — requests over the last 60 seconds, tokens over the last 1 second. Before every real dispatch (never for a cache hit), `waitForCapacity()` checks both windows and, if either is at its budget, waits until the oldest entry ages out; when capacity is free it reserves one request slot atomically, in the same synchronous step as the check, so two dispatches requested back-to-back by the concurrent scheduler cannot both slip through a stale check before either has reported its own usage. A dispatch's real cost — internal retry attempts beyond that one reserved slot, and the tokens actually billed — is folded in afterward via `recordDispatch`, once the real outcome is known (token cost can never be known before the provider responds, so it is necessarily reactive). `clock`/`sleep` are always injectable (`RunAuditOptions.clock`/`.sleep`), defaulting to the real clock and a real `setTimeout`-based wait — a test never sleeps on the real clock.

**Every work item's intended state is now durable, not only its finished state.** For every evaluable item, `runEvaluation` records a `pending` checkpoint up front — before the scheduler dispatches anything at all — then a `running` checkpoint the moment the scheduler actually picks that item up, then its terminal outcome (`completed`/`cached`/`failed`) once it settles; a `skipped` item (already known before the scheduler starts) skips straight to its terminal record, since it is never dispatched. Each is its own append-only `recordWorkItem` call — `pending`/`running` carry only `AuditStoreWorkItemIdentity`, nothing else — so a process killed at any point leaves a readable trail: an item that never started has only a `pending` row; one in flight when the process died has `pending` → `running`; one that finished has the full `pending` → `running` → terminal sequence. `AuditStorePort.lookup`'s `state = 'completed'` filter (P5-2) was re-verified against these new non-terminal rows and stays correct — a `pending`/`running` row never carries a cache key or an `attempts` row, so it was already excluded by the existing `INNER JOIN` to `attempts`, and this is now covered by an explicit regression test (`test/sqlite-audit-store.test.ts`) rather than left as an implicit invariant.

States remain `pending`, `running`, `completed`, `cached`, `uncertain`, `skipped`, or `failed` — the schema's `CHECK` constraint and the domain's `WORK_ITEM_STATES` admit all seven from the start (P5-1), so a later phase never needs a backward-incompatible migration just to widen it. `completed`, `failed`, and `skipped` were produced starting P5-1; `cached` starting P5-2, exactly once, on a cache hit; `pending`/`running` starting P5-3, as described above. `uncertain` remains undefined and unproduced — see "Persistence and cache" above. Only `completed` and a valid `cached` judgment participate in quality classification.

**Delivered (Phase 5, task P5-4): `--resume <runId>`.** `AuditStorePort` gains one new read method, `loadRunState(runId)` (`src/domain/audit.ts`), implemented by the sqlite adapter exactly along the lines P5-3 described: it selects every `work_items` row for `runId`, groups by `(test_case_id, repository_relative_path, name)`, takes each group's last (highest-`id`, `MAX(id)`, never `MIN(id)`) row, and — for the identities whose last row is one of the four terminal states — reconstructs the full `AuditStoreWorkItemOutcome` from `attempts`/`judgments`/`errors`/`skips`. An identity whose last row is `pending`/`running`, or with no row at all, is simply absent from the result: the port never decides what is "outstanding" itself, since only the caller (`runAudit`) knows which identities are currently evaluable or skippable at all. `loadRunState` also returns the run's own `rootDir` and whether `finishRun` was ever called (`finished`).

**Continuing a run, not widening `beginRun`.** Rather than change `beginRun`'s signature to accept an optional existing id, resuming simply skips calling it: `work_items.run_id` is a plain foreign key into an already-existing `runs` row, so appending more work items under the same `runId` needs no schema change and no new write method. `runAudit` reuses `options.resume` directly as the run id for every `recordWorkItem`/`finishRun` call in that pass.

**Preflight, before any discovery/extraction/evidence work at all** (`runAudit`'s `preflightResume`, mirroring its existing discovery-failure early return): `loadRunState(runId)` returning `undefined` throws `AuditResumeRunNotFoundError`; a `rootDir` mismatch against the root being audited now (see "rootDir identity", immediately below) throws `AuditResumeRootDirMismatchError`; a `finished` run returns immediately with an honest all-zero result and `resume: { runId, outstanding: 0, reused: 0, nothingOutstanding: true }` — not an error, and no discovery ever runs. All three error types (plus a defensive `AuditResumeUnavailableError` for a library caller that passes `resume` with no store at all, and `AuditResumeLegacyRootDirError` below) are caught by the CLI exactly like `AuditStoreSchemaVersionError`/`AuditStoreCorruptError` already are: a named message on `io`, exit code 1, no stack trace. The CLI reports the finished/nothing-outstanding case as `Nothing to resume: run <runId> has no outstanding work items.`, exit code 0.

**rootDir identity (defect fix, 2026-09-20).** P5-4's own initial implementation compared `state.rootDir !== request.rootDir` as raw strings, and `getResolvedConfiguration` defaults `rootDir` to the literal `"."` when `--rootDir` is not given. That produced two failures: a **false reject** (the same repository audited via two different-but-equivalent spellings — relative vs. absolute, a trailing slash, a symlinked ancestor — was wrongly rejected as a mismatch), and a **false accept** (two DIFFERENT repositories, each audited with no `--rootDir`, both stored the literal `"."` and compared equal — a `--resume` against repository B, using a run id minted for repository A, was silently accepted, writing B's work items into A's run and consulting A's cached judgments for tests that do not exist in B).

The fix canonicalizes `rootDir` at the store boundary, not inside `getResolvedConfiguration`: `AuditStorePort` gains `canonicalizeRootDir(rootDir): Promise<string>` (implemented by the sqlite adapter as `resolve()` then `realpath()`, following symlinks — the identical convention `discoverTestFiles`/`readSourceFile` already apply to the audited root; never throws, falling back to the plain resolved form when the path cannot be realpath'd). `runAudit` calls it BEFORE `beginRun` for a fresh run, so what gets PERSISTED is already canonical, and `preflightResume` calls it on the resume request's `rootDir` before comparing against the recorded value. Canonicalizing only at compare time was rejected: a stored `"."` would resolve against the resume-time working directory, which is exactly the wrong context (the false-accept scenario would resolve `"."` to repository B and match, preserving the bug) — the identifying value must be canonical when it is persisted, not re-derived later. Real-path resolution (not just `resolve()`) is necessary, not merely aesthetic: this project's own dev machine confirmed macOS routes its temp directory through a symlinked ancestor (`/var` -> `/private/var`), so two absolute-looking paths to the same repository would otherwise fail to compare equal. Canonicalizing inside `getResolvedConfiguration` instead was rejected as unnecessarily wide: `rootDir` also flows into discovery, the source reader, and evidence provenance, none of which this defect touches.

Backward compatibility: a run recorded before this fix has a `root_dir` that is not a canonical (absolute) value — most commonly `"."`. Re-resolving it now would resolve against the WRONG working directory (the same mistake as the compare-time-only rejected approach above), so it is never attempted. `AuditStoreRunState` gains `rootDirCanonical: boolean` (the sqlite adapter computes it as `isAbsolute(root_dir)` — a necessary, not sufficient, test: a pre-fix run whose `--rootDir` happened to already be absolute reads as canonical here even if it still traversed a symlinked ancestor `beginRun` never resolved, in which case it falls through to an ordinary, still-visible `AuditResumeRootDirMismatchError` rather than the legacy one). `preflightResume` checks this BEFORE the mismatch comparison and throws the new `AuditResumeLegacyRootDirError` when it is `false`: a named, visible usage error (exit 1) stating the run predates canonical root recording and cannot be resumed — never a silent fresh start, and never confused with a genuine cross-repository mismatch.

**Completing only the outstanding items.** `runEvaluation` partitions every currently evaluable item by identity against the resumed run's `terminalWorkItems`: a match on `completed`/`cached`/`failed` is reused directly — reconstructed into the same internal `EvaluationOutcome` shape a fresh dispatch produces (a reused `failed` item's error is replayed through a small `ResumedEvaluationFailure` carrying the original `errorKind`/`errorMessage`, so its `evaluation-failed` diagnostic reads identically to the one the interrupted attempt itself produced) — and merged back into `items`' own deterministic order; anything else (no match, or a match on `pending`/`running`) is dispatched exactly as before, with its own fresh `pending` checkpoint appended (an honest additional append, not a duplicate of the earlier one). A skipped item whose identity already carries a `skipped` terminal record is not re-recorded; one that does not (or whose only match is some OTHER terminal state — a currently-skipped item that used to be evaluable, or vice versa) is recorded fresh either way — skip/evaluable status is always freshly recomputed from the current source, resume or not, so this only affects which checkpoint writes are duplicated, never the reported totals. A currently-evaluable item whose ONLY match is a `skipped` terminal record (the audited source changed between the interrupted attempt and this resume — resume's documented assumption is an unchanged repository) is deliberately treated as outstanding rather than reused: it was never actually evaluated by the provider before, so there is nothing to reuse, and dispatching it for real is the safe degradation rather than a silently invented failure.

**The re-billing decision.** A `running` item's in-flight request may have already been answered by the provider before that answer was ever durably recorded — there is no signal available to this codebase, local or remote, that distinguishes "the request never reached the provider" from "it did, and the answer was lost with the process." Resuming re-dispatches it regardless, since that is the only correct choice given a never-recorded result; a resumed run can therefore cost slightly more than the work it visibly appears to redo. This is disclosed to the user in the CLI's `--resume` help text and in `README.md`'s "Resume" section, not silently absorbed.

**`--resume` and `--fresh` are orthogonal, by design, and the combination is defined.** `--resume` selects *which* items this invocation dispatches (only the outstanding ones); `--fresh` selects whether the items that *do* dispatch consult the cache first. They compose without special-casing: `cache.fresh` is threaded into `runEvaluation` exactly as before, and it is only ever consulted for an item that already reached the dispatch path — an already-terminal reused item never reaches cache lookup at all, `--fresh` or not, since reuse happens strictly before that branch.

**Reporting.** `AuditResult` gains an optional `resume: AuditResumeSummary` field (`{ runId, outstanding, reused, nothingOutstanding }`), present only when `RunAuditOptions.resume` was used. `--evaluate --json`'s payload carries the same three fields under a `resume` key; the human-readable report prints one extra summary line (`Resumed run <runId>: reused N already-completed item(s), dispatched M outstanding item(s).`). Neither changes shape for an ordinary (non-resume) `--evaluate` run.

## Reports

The versioned JSON schema is canonical. The HTML renderer (Phase 6, task P6-4) embeds that JSON and static assets into one offline file. CI always remains reporting-only in v1.

**Delivered (Phase 6, task P6-2): the canonical JSON report.** `audit --evaluate --json` no longer prints an ad-hoc, unversioned envelope — it prints `buildAuditReport`'s output (`src/domain/report.ts`), one pure domain function over an already-computed `AuditResult` plus a small caller-supplied `AuditReportContext` of build-time constants (the CLI's own `REPORT_CONTEXT`, `src/cli/index.ts`). This is a deliberate, intentional breaking change to `--evaluate --json`'s existing shape — the two hand-derived golden tests in `test/cli.test.ts` were updated to match, never loosened to a substring match — because Phase 6's Decisions treat the JSON report as the contract every later phase (Phase 7's benchmarks, and P6-4's HTML renderer) reads, and versioning it before anything consumes it is far cheaper than versioning it after.

**Four versions, never conflated.** `reportVersion` (currently `1`) is this envelope's own contract number. `versions.storeSchema` (`AUDIT_STORE_SCHEMA_VERSION`, re-exported from `src/adapters/sqlite-audit-store.ts` purely for reporting — a compile-time constant, present regardless of whether a store actually opened this run) is the persistence layer's own schema generation. `versions.rubric`/`versions.policy` are this build's currently active `RUBRIC_V2.version`/`CLASSIFICATION_POLICY_V2.version` pins. Each classification's own `rubricVersion`/`policyVersion` (unchanged, carried over from Phase 4) can differ from those active pins for an older cached judgment reused from before a rubric/policy bump — the report never claims they must agree.

**`complete: false` is exactly one predicate: `result.evaluation === undefined`.** In production wiring this fires only when `runAudit` returns before ever reaching `ports.evaluation` — a `discovery-failed` diagnostic aborting the whole pipeline before evaluation could start; `incompleteReason` then names that diagnostic (or a generic fallback when none is present, defensive for a foreign `AuditResult`). Every other candidate the feature document named — a failed work item, a resumed run, a model-pin mismatch, a `needs-review` verdict — is deliberately NOT incompleteness: each is already an ordinary, fully-disclosed per-test (or per-run-summary) outcome elsewhere in the same report (`totals.failed`, `resume.outstanding`/`reused`, `totals.modelMismatches`, `classification.status`), and `runEvaluation` drives every outstanding resumed item to a terminal state before `runAudit` ever returns — so a resumed `AuditResult` this function ever sees is, by construction, already fully resolved. This preserves the hard constraint proven by `test/cli.test.ts`'s existing `misleading`-exits-0 test and a new dedicated incomplete-run test: no finding and no infrastructure failure changes the exit status, complete or not.

**Per-test-case cache provenance and latency are new fields on `AuditEvaluationResult`** (`src/domain/audit.ts`), not something the report derives after the fact — `ClassificationResult` alone cannot tell a cache hit from a fresh success, so `runEvaluation` (`src/application/audit.ts`) now also returns `cacheStatusByTestCaseId: ReadonlyMap<TestCaseId, 'cached' | 'fresh' | 'not-evaluated'>` and `latencyByTestCaseId: ReadonlyMap<TestCaseId, TestCaseLatency>`, built in the exact same pass over `outcomes` that already computes `classifications`/`totals`, so the three can never disagree. The report's top-level `cacheStatus` array lists every evaluable test case exactly once (walked in `result.files`' own deterministic order, not the map's incidental insertion order); a skipped test case never appears there. Each `classifications[]` entry gets `cache` (always `cached`/`fresh` — a `not-evaluated` item never produced a `ClassificationResult`) and, only when a fresh dispatch's `JevEvaluation.latencyMs` was actually captured (P6-1), a `latency` object. The top-level `latency` aggregate (`measuredTestCases`, `totalMs`/`meanMs`/`minMs`/`maxMs`) is present in full only when `measuredTestCases > 0` — never a fabricated zero.

**Payload provenance now includes the actual denial/unresolved/omission decisions**, not only their counts: each classification's `evidence` field carries `denied`/`unresolved`/`omitted` as full lists (rule, specifier+reason, path+reason) alongside the existing `fragments`/`truncatedFragments` counts. Fragment *content* itself (the evidence bytes) remains out of the report — an open decision gap for P6-4 (see "Open questions" in the Phase 6 feature document), since a persisted/shareable HTML file sharpens the stakes on redaction already flagged for `--evaluate`'s error messages.

**Discovery decisions** are exposed via a new `discovery` block (`files`, `excluded`, `totals`) mirroring the plain (non-`--evaluate`) summary's own shape — absent from the pre-P6-2 report entirely.

**Schema validation without a runtime dependency.** `docs/report-schema.json` is the published, checked-in schema (a draft-07-shaped JSON Schema subset: `type`, `enum`, `properties`/`required`/`additionalProperties`, `items`), generated from the in-code `REPORT_JSON_SCHEMA` constant (`src/domain/report-schema.ts`) — a test (`test/report.test.ts`) asserts the two stay byte-identical. Validation itself is a small hand-rolled structural validator, not `ajv` or any other third-party library: this package ships zero runtime dependencies as a deliberate posture (Phase 6 Decisions), and a full JSON Schema implementation is far more machinery than validating one fixed, internally-produced shape needs. The validator is dev/test-only — nothing in the CLI's runtime path calls it.

**Delivered (Phase 6, task P6-2b): a fresh run's `runId` reaches the report, closing the `reports`-table question with no table.** P6-2 itself only threaded `resume.runId` (present exclusively for a `--resume`'d invocation) onto `AuditResult`; a fresh, non-resumed run's own store-minted id was discarded the moment `runEvaluation` returned. `AuditResult` now carries an optional top-level `runId` (`src/domain/audit.ts`) — the exact id `AuditStorePort.beginRun` minted for a fresh run, or the continued id for a resumed one (in which case it always equals `resume.runId`; `runAudit` never assigns the two independently, including through the already-finished-resume early return in `preflightResume`). `buildAuditReport` mirrors it verbatim onto the report's own `runId` as one more optional field, immediately after `rootDir` in the stable key order, present under the identical condition: a store was present for this run. Absent — never a fabricated placeholder — for an offline audit, an `--evaluate` run with no store wired, or a run whose evaluation never started at all. This is the orchestrator's own resolution to the gap P6-2 left open and the one the Phase 5 implementation plan's work unit 5 never designed (see `docs/implementation-plan.md`): a report is traced back to its persisted run, and correlated with a later `--resume`, by this one field alone — no `reports` lookup table is built, because nothing concrete needs one once the id already travels with the report that names it.

**What P6-4 can now rely on:** the canonical JSON alone (no repository, no database) already carries every datum named above — discovery decisions, full payload provenance decisions, scores/probabilities, all four distinguished versions, per-test-case cache status, usage, latency, errors, and (as of P6-2b) the run's own persisted identity — so an HTML renderer can be built as a pure function over one parsed JSON file. One thing it still cannot get from this JSON alone: fragment source content (deliberately excluded — see "Payload provenance" above).

**Delivered (Phase 6, task P6-4): the self-contained offline HTML report.** `--html <path>` renders `buildAuditReport`'s own output — the identical `AuditReport` `--evaluate --json` prints — into one HTML document via `renderAuditReportHtml` (`src/domain/html-report.ts`): a pure function, no I/O, no timers, no adapter imports (enforced by the same architecture-boundary test every other domain module is held to). Two adapters do the I/O this task needs: `src/adapters/html-report-writer.ts` (`checkHtmlReportPath`/`writeHtmlReport`) writes the file and decides the three named outcomes below; `src/adapters/html-report-opener.ts` (`viewerCommandFor`/`openHtmlReportWithViewer`) launches `--open`'s platform viewer.

- **Rendering strategy.** Every visible element is server-side string-templated, with every interpolated value passed through a small `escapeHtml` (`&`, `<`, `>`, `"`, `'`). The full report is ALSO embedded verbatim as inert JSON (`<script type="application/json" id="jev-report-data">`, escaped by replacing `<` with `<` so a payload's own `</script>` can never prematurely close the tag), but the page's own visible rendering never re-derives itself from that JSON at view time — the one small behavior script (vanilla, no framework, no third-party library) only filters and expands/collapses the already-rendered `<details>` elements. This keeps the whole renderer testable with plain string assertions; no `jsdom` dependency was added.
- **Self-contained, proven by category, not by example.** The test suite (`test/html-report.test.ts`) asserts the absence of an entire class of external-reference constructs — `<link>`, a protocol-relative or `http(s)` `src`/`href`, `<iframe>`/`<embed>`/`<object>`, `@import`/`url(…)` inside a real `<style>`/`<script>` block, `fetch`/`XMLHttpRequest`/`WebSocket`/`EventSource`/`sendBeacon` in the one executable script — including a test that deliberately smuggles a hostile `//evil.cdn.example` / `<link>` / `@import` string into report content (a diagnostic message, a test name) and confirms it renders only as inert, escaped text, never as a live tag or CSS directive. A naive substring check (grepping the WHOLE document for the literal word `@import`/`url(`) was tried first and produced a false positive against that same hostile fixture's escaped text — fixed by scoping those two checks to the actual `<style>`/executable-`<script>` block content, never plain page text.
- **Escaping, one fixture, every string field.** `test/html-report.test.ts`'s hostile-value suite puts `</script><script>alert(1)</script>"><img src=x onerror=1>&'quoted'` into every string-typed field the report has (`rootDir`, `runId`, `modelRequested`, discovery paths/framework, diagnostics, classification name/path, dimension label, evidence denied/unresolved/omitted rule/specifier/reason, `resume.runId`) and asserts the raw payload appears nowhere outside the embedded JSON block, that the document still carries exactly two `<script>`/`</script>` pairs (the payload's own `</script>` sequences never leaked through unescaped), and that the JSON block still round-trips byte-for-byte to the original fixture.
- **A self-deceiving test caught and fixed before being reported.** An early "shows the incomplete banner" assertion checked `html.toLowerCase()).toContain('incomplete')` against the WHOLE document — which is trivially satisfied by the embedded JSON's own `incompleteReason` KEY NAME (which contains the substring "incomplete"), regardless of whether the visible banner markup rendered at all; disabling the banner's own render function entirely left the test green. Fixed by stripping the embedded JSON script block before any assertion whose actual claim is "a reader can SEE this" (`visibleHtml()`, a shared test helper) and asserting the specific applied class (`div class="banner banner-incomplete"`), not a bare class-name substring (which the page's own `<style>` block also always contains, for an unrelated reason — its CSS rule definition).
- **Renders from JSON alone, proven with a real disk round-trip.** `test/html-report.test.ts` writes a hand-built report to a temp JSON file, asserts the audited repository path it names (`rootDir`) genuinely does not exist on disk, `JSON.parse`s the file back, renders from that parsed value, and confirms no other file (a database, a sidecar) appeared in that directory as a side effect — making "no repository, no database" a checked fact, not an assumption the test's own setup happens to hold.
- **Worst-first structure.** Classifications are re-sorted `misleading` → `weak` → `needs-review` → `healthy` (a stable sort, never mutating the caller's array); a `not-evaluated` `cacheStatus` entry (dispatched but the request itself failed — never produced a `ClassificationResult` to attach a verdict to) gets its own small block positioned before the ordinary classification list, so a failed dispatch — unknown, not healthy — is never left below a page of healthy verdicts.
- **No fragment content**, matching the JSON report's own posture (see "Payload provenance" above): only the provenance decisions and counts already on `AuditReportEvidenceProvenance`.
- **Overwrite, directory, missing parent — the three named `--html <path>` outcomes** (`src/adapters/html-report-writer.ts`): an existing regular file is silently overwritten (the established CLI convention for an explicitly named output path; disclosed on stderr, never stdout); an existing directory, or a path whose parent does not exist, is a usage error (exit 1, readable message, no stack trace) — preflighted in `src/cli/index.ts` BEFORE any evaluation work is dispatched (so a bad path costs nothing), and re-checked at write time regardless (the unavoidable TOCTOU race between preflight and the real write). No parent directory is ever auto-created — unlike this tool's own owner-only config directory, `--html <path>` is an arbitrary user-supplied filesystem path, and silently creating a directory tree there on a typo'd path was judged a surprise this tool's "nothing happens unless explicitly asked for" posture argues against. The file itself gets no restrictive permissions of its own (unlike the credentials file's `0o600` or the audit store directory's `0o700`) — it is explicitly built to be handed to someone else.
- **`--open`, per platform** (`src/adapters/html-report-opener.ts`): `open <path>` on macOS, `xdg-open <path>` on Linux, `explorer.exe <path>` on Windows (deliberately not `cmd /c start "" <path>` — `start`'s quoting through `child_process.spawn` without `shell: true` was judged too murky to get right; `explorer.exe <path>` needs no quoting decision at all). Spawned `detached`, with stdio ignored, `unref()`'d the moment either the child's own `'spawn'` or `'error'` event fires — the CLI never blocks on the viewer, and a failure (most commonly: no viewer installed, the ordinary CI case) is reported on stderr only and never changes the exit status or touches the already-written file. This deliberately never waits for or interprets the viewer's own exit code — only "could the OS start a viewer process" is answered, never "did a human see a window," which nothing available here can prove either way; disclosed, not hidden. The win32 path is exercised only at the pure `viewerCommandFor` level in this project's own suite (no Windows CI) — the same disclosed-limitation posture already taken for the untested TTY redraw path (P6-3, `terminal-progress-reporter.ts`).
- **Both the write confirmation and any `--open` failure go to stderr, never stdout** — exactly like progress (P6-3): `--evaluate --json`'s stdout stays byte-clean, exactly one canonical JSON line, regardless of whether `--html`/`--open` were also given.
- **The API key never reaches the file**, proven the same way the JSON/database canaries already are: the real gateway resolves and sends a canary key (never a stubbed evaluation port, which would bypass key resolution and make the assertion vacuous), and the written HTML is asserted not to contain it.

## Progress

**Delivered (Phase 6, task P6-3): terminal progress during a run.** A long `--evaluate` run previously printed nothing until it finished — the first real run took roughly 1.9 seconds for 11 test cases at concurrency 4, and a repository with thousands will run long enough that silence reads as failure (this phase's own feature document). `runEvaluation` (`src/application/audit.ts`) now notifies an optional `AuditProgressPort` (`src/domain/audit.ts`) at exactly the same checkpoint call sites `AuditStorePort.recordWorkItem` already fires from — `skipped`, `pending`, `running`, then a terminal `completed`/`cached`/`failed` — in real completion order under concurrency, never sorted or batched to the end.

**Independent of the store, by design.** `progress` is threaded onto `runEvaluation` as its own optional parameter, gated on nothing but its own presence — never on `store`/`runId` being present too. Every `store.recordWorkItem` call site was restructured so the store write (still gated on `store !== undefined && runId !== undefined`, unchanged) and the progress notification (never gated on that) sit side by side rather than sharing one `if` block; the progress call always comes immediately after the (possibly skipped) store write, so a reported transition never precedes its own durable record when one exists. This is what lets a `--evaluate` run with no store wired still report every transition exactly as if one were present — progress describes what the run is doing, not what gets persisted.

**`begin(total)` names the real denominator.** Fired exactly once, before any per-item transition, with `skippedToRecord.length + outstandingItems.length` — the count of work items that will actually reach a terminal state THIS run. A resumed run's already-terminal, reused items are deliberately excluded (never `items.length` unconditionally): they are never redispatched and never call `report` again, so counting them would make "N of TOTAL done" lie by never reaching TOTAL.

**Two counted properties survive to the adapter: cache status and concurrency.** Each `AuditProgressEvent` carries `state` (one of the six real checkpoint states — `uncertain` is excluded by `Exclude<WorkItemState, 'uncertain'>`, the identical posture `WorkItemState`'s own doc already takes) and `concurrencyLimit`, the adaptive scheduler's own `controller.limit` read at the exact moment of that transition. Because `runAdaptiveSchedule` (`src/application/scheduler.ts`) applies a dispatch's throttle signal to the controller only in its own `.then` handler, AFTER the worker's promise has already settled, a throttled dispatch's own terminal event still carries the PRE-reduction limit; the reduction becomes visible starting with the very next dispatched item's own `running` event, never retroactively on an event already reported. This is deliberate, not an oversight, and is pinned by a dedicated test (`test/progress.test.ts`) that resolves a throttled item and a clean sibling in a controlled order and asserts both values.

**The adapter, not the port, decides what gets rendered.** `createTerminalProgressReporter` (`src/adapters/terminal-progress-reporter.ts`) is the one place a real byte is written; `write`/`isTTY` are both injected, so the CLI (`src/cli/index.ts`) is the only place either is bound to a real stream (`process.stderr.write`/`process.stderr.isTTY`) — `CliDependencies.createProgressPort` is the test seam, gated exactly like `createEvaluationPort`/`createStorePort` (only constructed once evaluation was requested and a usable API key already resolved). Progress is always on stderr, never stdout: `--evaluate --json` prints its one canonical report line to stdout, and this tool's zero-runtime-dependency, zero-configuration posture extends to progress having no flag to redirect or disable it — a consumer piping stdout already gets byte-clean JSON without doing anything, and `2>/dev/null` is available to anyone who wants silence.

- **Interactive terminal**: one status line, redrawn with a bare `\r` on every checkpoint (`N/TOTAL done (fresh F, cached C, failed X, skipped S, limit L)`), terminated with `\n` only once `doneCount` reaches `total` — which, by construction, can only happen on the chronologically LAST event this run ever produces.
- **Non-interactive output** (a pipe, a CI log, a redirected file): one clean, `\n`-terminated line per TERMINAL transition only — `pending`/`running` produce no output, since a `\r` redraw would just accumulate as garbage and neither carries new terminal information. Each line names the item (`repositoryRelativePath :: name`, sanitized: embedded `\r`/`\n` in a hostile or merely unlucky test name are replaced with a space, so one transition is always exactly one output line) plus the same running counts — a cache hit (`cached`) is always visible as distinct from a fresh dispatch (`completed`).

**No opt-out flag.** Considered and declined: the non-TTY contract above already guarantees a piped `--json` consumer's stdout stays byte-clean regardless of whether progress is enabled, so a flag would exist only to silence stderr — which `2>/dev/null` already does, at the shell, for any command. This repository's own convention ("prefer not adding a flag you cannot justify," this phase's own feature document) is why none was added.

## Deterministic evaluation

Fixture operators introduce one known change, such as removing an assertion, weakening an expectation, adding shared state, mocking owned logic, pinning an implementation detail, or introducing uncontrolled time. Executable oracles validate the expected effect through production mutation, assertion mutation, semantics-preserving refactoring, or repeated/randomized execution.

Only dimensions proven by an operator and oracle count toward accuracy. Unproven real-world observations remain `unverified`. Jev never labels its own benchmark.

**Delivered (Phase 7, task P7-1): the corpus format and its parser, storing declarations only — no mutation applied, no oracle run, no provider call.** `src/domain/corpus.ts` is pure (no Node imports, no adapter imports, exactly like every other `src/domain` module — enforced by `test/architecture-boundary.test.ts`) and parses one case's already-read manifest bytes; `src/adapters/corpus-store.ts` does the actual disk I/O (reading `case.json` plus the files it names) and hands the result to the domain parser, never deciding shape itself.

A case's operator and its oracle name two independent mutation targets, not one: the six operators above all mutate the *test*. Three of the four oracle kinds act on *production* (mutate the function, refactor it while preserving behavior, run repeatedly/randomized); the fourth, assertion mutation, acts on the base test's own assertion and compares outcomes instead. Each case therefore declares `operator` (exactly one of the six — a manifest naming two or zero is rejected), `operatorRole` (`'prescriptive'` if P7-2 is expected to actually apply the operator to the base test to produce a variant, `'descriptive'` if it merely names a flaw already present in the base test as written — required and explicit, because `oracleKind` cannot reliably carry this: `checkout-applies-percent` is `production-mutation`, the same oracle kind as several `'descriptive'` cases, yet it is `'prescriptive'`), `oracleKind` (exactly one of the four, required so a case that is merely undecided about how it will be proven is a rejected manifest, not a silently accepted one), `testEffect` (what the operator changes about the base test), `productionEffect` (the falsifiable pass/fail claim the named oracle is meant to prove, whichever side it acts on — both effect strings required and non-empty), and `expectedOutcome` (`'expected-to-fail'` or `'expected-to-keep-passing'`, a raw, oracle-kind-agnostic prediction of whether the base test's own result flips to failing once its oracle acts — the same prose claim in `productionEffect`, made structural so P7-2/P7-4 can verify and score it by comparison instead of parsing prose; not a quality judgment, since `spies-on-math-round`, a deliberately bad `'descriptive'` case, still predicts `'expected-to-fail'`). `CorpusCase.proofStatus` is always `'unverified'`, a literal the parser assigns itself; a manifest cannot declare it (an unknown top-level field, including a hand-authored `"proofStatus": "proven"`, is rejected), so a corpus case's claim about itself can never be mistaken for a demonstrated proof. P7-2 introduces the proven counterpart once an oracle can run for real.

On-disk shape: one directory per case (`test/fixtures/corpus/<suite>/<case-id>/`) holding a small `case.json` sidecar plus the base test and every production file as their own real, byte-exact `.ts` files (never inlined into a JSON blob) — chosen over a single manifest-of-blobs specifically so a case's history is reviewable as ordinary diffable source in Git, and so a later proof can be re-run against the exact committed bytes that produced it. Base-test files are named `test.ts`, never `*.test.ts`/`*.spec.ts`, so Vitest's own default collection never executes them; only `npx vitest run` against the real, dedicated test files (`test/corpus.test.ts`, `test/corpus-store.test.ts`) ever reads them, and only by calling `loadCorpusCase`/`loadCorpusFromDirectory`, never by import.

`test/fixtures/corpus/discrimination/` expresses the existing intent-labelled `test/fixtures/discrimination/cart.test.ts` (11 tests, 3 good controls and 8 deliberately bad, one per rubric criterion) in this new format — the originals are untouched for comparison. Each of the 11 gets its own case directory, its own extracted single-test `test.ts`, and a declared operator/oracleKind/testEffect/productionEffect pair; the mapping from rubric-era intent to operator is this task's own analysis of what each test actually does, not a re-run of any oracle. The ported set does not exercise `introduce-uncontrolled-time` (the original fixture uses unseeded randomness and shared module state, not real wall-clock time) — a real gap Phase 7 should decide whether to backfill with an authored case rather than force an ill-fitting label onto an existing test.

**Delivered (Phase 7, task P7-2): proving each operator by execution.** `src/domain/oracle.ts` (pure, no I/O, no timers, no process spawning — enforced by the same `test/architecture-boundary.test.ts` every domain module is held to) turns one already-parsed `CorpusCase` into an `OraclePlan` (`buildOraclePlan`) and, separately, decides whether a case's declared claim held from a set of recorded observations (`decideProof`) — never a bare boolean, always `'proven'` or `'unproven'` with a specific reason. `src/adapters/oracle-runner.ts` is the one place in this repository that spawns a test runner: it materializes one `OracleRun`'s files into a fresh `fs.mkdtemp` scratch directory *outside* the repository (never inside `test/fixtures/corpus/`), symlinks that scratch directory's `node_modules` to this package's own (resolved via `import.meta.resolve('vitest/package.json')`, never a hardcoded path), spawns an isolated vitest subprocess against it with an explicit, allow-listed environment (`buildChildEnv` — `PATH`/`HOME`/`TMPDIR` and friends only, deliberately never a spread of `process.env`, so the outer suite's own `VITEST`/`VITEST_WORKER_ID`/`NODE_ENV` never leak into the child), enforces a timeout by killing the whole process group (`detached: true` + `process.kill(-pid, 'SIGKILL')`), and reads vitest's own `--reporter=json --outputFile=<path>` report to distinguish a genuine assertion failure from a load/parse error (`assertionResults.length !== expectedTestCount`) or a timeout — never misreporting either as a plain pass or fail. The scratch directory is always removed in a `finally` block, on every outcome. `src/application/benchmark.ts` (`proveCase`/`proveCorpus`) orchestrates the two through one injected `OracleObservationPort`, exactly like `src/application/audit.ts` orchestrates `AuditPorts`.

**Every case runs a `'baseline'` first**, against its own unmutated production code — the Decisions' "a base test that genuinely passes against its production code" claim, never executed before P7-2. A case whose baseline does not pass is `'baseline-failed'`, regardless of any later observation.

**`oracleKind` does not change the mechanical procedure P7-2 runs**, reading each of the 11 real cases' own `productionEffect` prose: every `'descriptive'` case (`oracleKind` `production-mutation` or `semantics-preserving-refactor`) is proven by one declarative production-side transform plus a single run of the unmodified base test against it. Every `'prescriptive'` case (`oracleKind` `production-mutation` or `assertion-mutation`) is proven by the same two-run comparison regardless of which `oracleKind` it declares: the unmodified base test against one fixed production mutation (expected to flip to failing, matching its declared `expectedOutcome`, which must be `'expected-to-fail'` — a prescriptive case declaring `'expected-to-keep-passing'` is `'incoherent-declaration'`, decided without even inspecting the variant), then the operator-derived *variant* test against that *same* mutation (expected to keep passing — `'operator-did-not-hide-defect'` if it does not). `'repeated-randomized-execution'` (exactly one real case, `records-history-shared-state`) is the one genuinely different shape: its `describe(...)` block is duplicated (`duplicateDescribeBlock`) so two `it(...)`s share one module load in one process, against a production mutation that only breaks `record` from its second call onward (`record-only-first-call`) — proving the first call's leftover state masks the second call's broken one, exactly as that case's own `productionEffect` claims.

**Declarative, named, anchor-checked mutations**, per this task's own instruction to prefer a small set of deterministic mutations over a general engine: every production mutation and every prescriptive-operator test variant is one named `TextTransform` (`PRODUCTION_TRANSFORMS`/`TEST_VARIANT_TRANSFORMS` in `src/domain/oracle.ts`) — an exact substring replaced by fixed text, applied by `applyTextTransform`, which throws unless its anchor occurs in the source *exactly* once. Every anchor/replacement is taken verbatim from the corresponding case's own `case.json` "(for example ...)" prose. A case id with no registered recipe, or whose transform's anchor no longer matches its committed bytes, is `'unrealizable'` (`no-mutation-declared` / `mutation-anchor-not-found`) at plan-build time, before anything is spawned — never a silently unmutated or silently-passing plan. The case id -> recipe binding lives in a domain-side registry rather than a new `case.json` field, an explicitly returned open decision (retrofitting P7-1's manifest and parser was out of this task's authorized scope).

**Proof is recorded as data**: `CaseProof` (`src/application/benchmark.ts`) carries every run's label, which files it mutated, the observed `Observation`, and a sha256 `contentHash` of the exact bytes that produced it — computed directly from the run's own files, so it never depends on the execution having happened correctly to be trustworthy. All 11 real corpus cases are proven exactly as their own `expectedOutcome` predicts (`test/oracle-corpus-integration.test.ts`, verified against the live corpus). The acceptance criterion this whole phase exists for — a case whose mutation does not produce its declared effect is reported unproven, never silently proven — is proven with a deliberately mispredicted clone of a real, genuinely-passing case, asserted to come back `'unproven'` with `'prediction-not-held'` while its own underlying observation is shown to have genuinely kept passing (not merely stubbed).

**Reachability, proven, not asserted.** `src/cli/benchmark.ts` is its own CLI entry, never imported by `src/cli/index.ts` (the `audit` command). `test/benchmark-cli-boundary.test.ts` proves this by static TypeScript-AST import-graph closure — the same technique `test/architecture-boundary.test.ts` already uses — asserting the closure from `src/cli/index.ts` never contains `src/adapters/oracle-runner.ts` or `src/cli/benchmark.ts`, *and*, as a positive control, that the closure from `src/cli/benchmark.ts` does contain the runner (so the negative assertion cannot pass merely because the runner does not exist or is never imported from anywhere). No `package.json` `bin` entry was added for `benchmark` (a product decision returned, not made here); it runs today via `node dist/cli/benchmark.js` after `npm run build`. P7-2 also deliberately does not add `vitest` to `dependencies` (it stays a devDependency): the benchmark command is a maintainer/development-only surface, run against a full `npm ci` checkout of this repository, never something an installed end-user build of `jev-test-auditor` needs — also returned as an open decision rather than silently changed.

## Benchmark agent-review skill

The repository includes a development skill, not a product runtime dependency. Given an immutable completed benchmark run, it selects disagreements, regressions, and calibrated samples, then shards them across lightweight read-only subagents provided by the active Codex or Claude environment. It never owns API credentials or calls a second model from the CLI.

First-pass workers receive the test, minimal production context, rubric, and available deterministic oracle proof, but not Jev's verdict. They return a structured assessment with evidence and uncertainty. After those results are frozen, a comparison stage may see both outputs to classify likely model error, rubric ambiguity, context-selection error, or unsupported disagreement.

SQLite records the skill version, worker runtime/model identity when available, immutable input hashes, prompts, structured findings, and comparison outcome. These judgments guide rubric refinement but do not become ground truth unless an executable oracle independently proves the claim. Normal audits never invoke this skill.

## Security and failure boundaries

- Credentials come from supported environment or local credential storage and never enter reports.
- Symlinks and resolved paths cannot escape the repository root.
- Payload and report size limits are explicit; truncation is recorded.
- Database writes use transactions and migrations; corrupt or incompatible stores fail visibly.
- API, parser, extraction, and rendering failures remain distinguishable.
- No finding or infrastructure failure changes the CI exit status because v1 is reporting-only.

## Evolution

Future language support replaces discovery, extraction, and executable-oracle adapters. The rubric concepts, scheduler, persistence, classification, and report contracts remain reusable only where benchmarks demonstrate equivalent meaning; the design avoids a speculative public plugin API in v1.
