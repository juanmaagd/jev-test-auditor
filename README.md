# jev-test-auditor (`jta`)

`jev-test-auditor` (executable command: `jta`) is a local-first CLI for auditing the semantic quality of existing JavaScript and TypeScript tests. The pipeline discovers supported test files, reads them without executing project code, extracts deterministic structural test understanding, and — for every extracted test case — selects a minimal, provenance-aware local evidence bundle (the test body plus the smallest useful helper and production fragments it references). By default nothing built here is sent anywhere: discovery, extraction, evidence selection, and the default `audit` summary are entirely offline and need no API key. Real Jev evaluation is opt-in only (`audit --evaluate`, see below) — nothing leaves this machine unless that flag is passed, and `--evaluate` also persists its results to a local SQLite database, reuses an unchanged test's prior judgment instead of paying for it again, dispatches through an adaptive scheduler that reduces concurrency under real provider throttling and observes request/token budgets, and can resume an interrupted run by its run id instead of starting over (see "Audit store", "Content-addressed caching", "Adaptive scheduling and resilience", and "Resume" below).

## Installation

Requires Node.js **>= 22.13.0** (`node:sqlite` persistence without experimental flags).

### Automated install via curl

```bash
curl -fsSL https://raw.githubusercontent.com/juanmaagd/jev-test-auditor/main/install.sh | sh
```

### Install via npm / pnpm / bun

```bash
# Install globally
npm install -g jev-test-auditor

# Or run directly on demand
npx jta audit
```

## Setup: TypeSafe API Key

Semantic evaluation with Jev (`jta audit --evaluate`) requires a **TypeSafe API key**.

> [!IMPORTANT]
> **Discovery, parsing, and dry-run estimates (`jta audit`, `jta audit --dry-run`) work 100% offline without any API key.**
> However, to evaluate test semantics with Jev and generate offline HTML reports (`jta audit --evaluate --html ...`), a TypeSafe API key is required.

### 1. Interactive configuration (Recommended for developers)

Run `jta auth login`. It securely prompts for your key without echoing characters to the terminal, and saves it locally with owner-only permissions (`chmod 600`):

```bash
jta auth login
```

Check configuration status at any time:

```bash
jta auth status
```

To remove the stored key:

```bash
jta auth logout
```

### 2. Environment variable (Recommended for CI/CD)

Set the `TYPESAFE_API_KEY` environment variable in your terminal session or CI secrets:

```bash
export TYPESAFE_API_KEY="your-typesafe-api-key"
```

When `TYPESAFE_API_KEY` is present, it automatically takes precedence over any locally stored key.

## Quick path

From any project repository:

```bash
# 1. Inspect tests offline without executing project code (no API key needed)
jta audit

# 2. Preview billable calls and input-token/USD cost estimates (no API key needed)
jta audit --dry-run

# 3. Configure your TypeSafe API key (one-time setup)
jta auth login

# 4. Run real semantic evaluation and open the self-contained offline HTML report
jta audit --evaluate --html --open   # writes ./report.html
```

From this repository's own development checkout:

```bash
npm ci
npm test
npm run typecheck
npm run build
npm run lint
node dist/cli/index.js --help
node dist/cli/index.js audit
```

The audit command prints one human-readable, reporting-only summary — discovered/excluded files, evidence provenance, diagnostics, and the same no-network, no-write cost/call estimate `--dry-run` computes (see the `audit` and `audit --json` rows below). It does not execute tests or call an evaluator.

| `audit --evaluate --resume <runId>` | Continues a previously started run instead of starting a new one: reloads that run's outstanding work items (anything that never reached `completed`/`cached`/`failed`/`skipped`) and completes only those, leaving every already-terminal item untouched and never re-dispatched. `audit --json`'s totals include evidence counters (`evidenceBundles`, `evidenceFragments`, `evidenceTruncatedFragments`, `evidenceOmitted`, `evidenceDenied`, `evidenceUnresolved`), and each file entry carries an evidence bundle count. The default report's own text prints `Evidence fragments`/`Evidence omitted`/`Evidence denied`/`Evidence unresolved`, but deliberately not a separate `Evidence bundles` line: in the common case it is the same number as `Discovered test cases` (one evidence bundle per discovered test case) under a different name, so the report states it once rather than twice. Bundle *contents* — fragment text, spans, hashes — never appear in either report; only `--inspect-payloads` prints them.

**An unattributable framework is reported, never silently counted as zero tests.** A discovered, included test file whose framework cannot be attributed (no recognized import, or conflicting evidence — e.g. both Jest and Vitest imported) and that yields zero test cases produces one `unsupported-framework` warning diagnostic naming the test-framework-looking imports actually found (e.g. `node:test`), or stating plainly that none were found. It is merged into both that file's own diagnostics and the root `diagnostics`, exactly like an extraction diagnostic, and `totals.unsupportedFrameworkFiles` counts how many files carry one — so a reader sees "we don't understand this framework" without reading every record, instead of a report that reads identical to a genuinely empty repository. A recognized framework with genuinely zero test cases (an empty Vitest helper file, say) never produces this warning — it is about silence, not about the framework alone, and it never invents a framework or a test case.

**A file with no test-framework import still gets attributed from the project's own configuration, as a fallback.** Jest's standard setup (and NestJS's default one in particular) leaves `describe`/`it`/`expect` as ambient globals — no `@jest/globals` import ever appears — so import-based attribution alone leaves every such file `unknown` even though it plainly extracted real test cases. Once a file's own imports attribute nothing, `jev-test-auditor` falls back to the nearest ancestor `package.json`'s `jest` key, a `"test": "jest"`-style runner script, or a `jest.config.{js,cjs,mjs,ts,json}` file's presence (never its content for the JS/TS variants — see `src/adapters/jest-project-config.ts`) to attribute `jest`. This ancestor search deliberately crosses `--rootDir` itself (e.g. `--rootDir` pointing at one module inside a larger repo, with `package.json` only at the real project root): it stops at the first `package.json` found, or at a directory's own `.git` boundary, whichever comes first. Import-based attribution always wins — this fallback only ever runs when a file's own imports attributed nothing — and conflicting project evidence (a `vitest` dependency, a `"test": "vitest"`/`"test": "bun test"` script, or a `vitest.config.*` file) keeps the file `unknown` rather than guessing. Because this reads project configuration, not the file itself, and discovery's own per-file `frameworkEvidence` list (`'import' | 'package'` sources) is unchanged, a file attributed this way reports `framework: 'jest'` with an empty `frameworkEvidence` in `audit --json`.

**`bun:test` is a fully supported V1 framework, not just recognized evidence.** A file that statically imports (or `require`s) `bun:test` attributes framework `bun` and extracts the same suite/case/modifier/hook/mock/assertion/parameter-table structures Jest and Vitest do, including `test.serial` (preserved as its own modifier kind — bun-only, no Jest/Vitest equivalent) and the `mock`/`spyOn`/`jest` surface bun re-exports (recorded under a `bun.`-prefixed `MockApi`, e.g. `bun.mock.module`, `bun.jest.fn`, so a bun-provenanced call is never confused with real Jest). Conflicting framework evidence in the same file (e.g. both `bun:test` and `vitest` imported) stays `unknown`, exactly like a Jest/Vitest conflict. Still deliberately out of scope: `*_test.*`/`*_spec.*` filename patterns and the `.mjs`/`.cjs`/`.mts`/`.cts` discovery extensions bun also supports — a file only reaches extraction once discovery's existing `.test`/`.spec` JS/JSX/TS/TSX pattern matches it.

## Local API key storage (`auth login` / `auth status` / `auth logout`)

`--evaluate` needs a TypeSafe API key. Local storage is a per-user file scoped to this tool, not a global environment variable — `TYPESAFE_API_KEY` remains supported and is checked first, so CI keeps injecting it as a GitHub repository secret.

- **Precedence**: `TYPESAFE_API_KEY` (non-blank) wins whenever it is set, so CI/automation setups are unaffected; otherwise the locally stored file's key is used; otherwise `--evaluate` is a usage error (exit 1, no network attempted) that names both ways to provide a key.
- **`auth login`** reads the key from a no-echo interactive prompt when stdin is a TTY (raw mode, no character echoed, Ctrl+C cancels cleanly and always restores the terminal), or one trimmed line from stdin otherwise, so scripted/CI setup can pipe a key in. The key is **never** accepted as a command-line argument — that would leak it into shell history and the process list. A blank/whitespace-only key is rejected; nothing is written.
- **`auth status`** reports whether a key is available, which source would win (`environment` or `stored`), and the stored file's path and permission state. It never prints the key, or any part of it (no masking, no last-four characters).
- **`auth logout`** deletes the stored file and reports honestly whether one existed.
- **Storage location**:
  - POSIX: `$XDG_CONFIG_HOME/jev-test-auditor/credentials.json`, or `~/.config/jev-test-auditor/credentials.json` when `XDG_CONFIG_HOME` is unset.
  - Windows: `%APPDATA%\jev-test-auditor\credentials.json`.
  - The containing directory is created with mode `0o700` and the file with mode `0o600`, both set **at creation** (never write-then-`chmod`, which would leave a window where the file is world-readable) via a temp-file-plus-atomic-rename sequence.
  - On POSIX, a stored file whose permissions are more permissive than owner-only is refused (fail closed) rather than silently trusted — `auth status`/`--evaluate` report the problem and how to fix it (`chmod 600 <path>`, or `auth login` again to recreate it).
  - **Windows does not enforce file permissions.** This tool does not verify or claim to verify them there; `auth status` says so plainly.
- **The stored file holds the key in plaintext**, readable by any process running as the same user. A system keychain was considered and deliberately deferred (Phase 4 Decisions) — do not treat this file as hardened secret storage. Prefer `TYPESAFE_API_KEY` for shared/CI machines.
- **CI guidance**: add the key as a GitHub repository secret and inject it as the `TYPESAFE_API_KEY` environment variable in the workflow step that runs `audit --evaluate`. `auth login`'s interactive prompt is for local developer use only.

## Jev evaluation (`audit --evaluate`)

`--evaluate` is opt-in only. Without it, `jev-test-auditor` never leaves this machine: no gateway is constructed, no API key is read, and no network call is ever attempted — proven by tests that stub `fetch` to throw during a real audit run. Passing `--evaluate`:

- **Costs money and sends evidence to TypeSafe.** Every evaluable test case's local evidence bundle (test body plus its minimal helper/production-seam fragments and provenance — never the whole repository, never audited code executed) is sent as one Jev request, batched with all 14 rubric questions (`RUBRIC_V2`, the shipped rubric as of `odd/tasks/classification-calibration.md` task C-2, which repairs the `determinism-isolation`/`falsifiability` applicability questions; `RUBRIC_V1` is kept only for replaying the pre-C-2 recorded evidence). Pricing is USD 0.042 per 1,000,000 input tokens (output tokens are unbilled); see `JEV_ESTIMATE_SNAPSHOT` in `src/domain/estimate.ts` and `audit --dry-run` for a no-network cost preview before spending anything for real. **The rubric's own questions dominate a request's bytes, not the evidence** — the first real run (11 requests, 2026-09-20, under `RUBRIC_V1`) measured the rubric text at ~93% of the average request's bytes, which is why `--dry-run` measures the real request instead of estimating from evidence bytes alone (see below).
- **Requires a TypeSafe API key** from `TYPESAFE_API_KEY` or `auth login` (see "Local API key storage" above) — never logged, printed, serialized, or included in any report or error message. Having neither is a usage error (exit 1) before any request is attempted.
- **Runs with adaptive concurrency**: starts at configuration's `concurrency` (default 4), never exceeding it, and reduces or restores automatically under real provider throttling — see "Adaptive scheduling and resilience" below.
- **Never fabricates a verdict.** A failed evaluation (rate limit, timeout, malformed response, etc.) produces one `evaluation-failed` diagnostic naming the test case and the error's typed kind — never the API key or the request body — and contributes no classification; it is never counted as healthy.
- **Classification thresholds are provisional and versioned, not calibrated claims.** See "Classification policy" below for how a dimension's level and the overall verdict are actually decided, and the measured results recorded there.
- **`needs-review` means uncertainty, not a passing or failing grade.** It covers a model-pin mismatch, a dimension with a low-confidence or missing answer, or a test case where every dimension came back not-applicable — insufficient evidence or certainty, never an invented score.
- **A model-pin mismatch is always reported, never hidden**: every request pins the exact `jev-1.13.0` model id, and each classification's `model.matchesPin` — plus the run-level `modelMismatches` count in `--evaluate --json` — surfaces any response that answered with a different model.

## Progress during a run (`audit --evaluate`)

A long `--evaluate` run prints nothing else until it finishes, so (Phase 6, task P6-3) `--evaluate` now reports per-item progress as it happens, attached to the same `pending`/`running`/`completed`/`cached`/`failed`/`skipped` checkpoint trail the audit store already writes (see "Audit store" below) — never a second, independently derived notion of what happened. Progress is **always on stderr, never stdout**, and there is no flag to disable it: its non-TTY behavior below already keeps a piped `--evaluate --json` consumer's stdout byte-clean without anything to turn off. It never depends on the audit store being wired at all — a `--evaluate` run with no store still reports every transition, because progress describes what the run is doing, not what gets persisted.

- **Interactive terminal**: one status line, redrawn in place (`\r`, no scrollback spam) — `N/TOTAL done (fresh F, cached C, failed X, skipped S, limit L)` — updated on every checkpoint, terminated with a newline only once every item has reached a terminal state. `limit` is the adaptive scheduler's own current concurrency ceiling (see "Adaptive scheduling and resilience" below), which P5-3 can reduce or restore mid-run — showing it explains a run visibly slowing down without a second call.
- **Non-interactive output** (a pipe, a CI log, a redirected file — anywhere a `\r` redraw would just accumulate as garbage): one clean, newline-terminated line per **terminal** transition only (`completed`/`cached`/`failed`/`skipped`; `pending`/`running` produce no line, since they carry no new terminal information a log reader needs), naming the item's path and name plus the same running counts. A cache hit (`cached`) is always visible as distinct from a genuinely fresh dispatch (`completed`) — materially different to anyone watching provider cost accrue.
- **The API key never reaches progress output**, exactly like every other output this tool produces.

### Pre-dispatch phases (T3, `odd/tasks/audit-run-responsiveness.md`)

Before any of the above, `runAudit` discovers, reads, extracts, and selects evidence for every test file — 15–20s of CPU with no output at all on a large suite (~7,000 test cases), since none of that work is per-item dispatch. `--evaluate` now reports three coarse pre-dispatch milestones on the same stream, so a long run shows something from its first second:

- **`Discovering test files...`** once, before discovery itself has even resolved (nothing else is known yet).
- **`Extracting test cases: D/T files (N test case(s) found)...`** as `runAudit` works through the discovered files — extraction and evidence selection are reported together, not as two alternating phases, since they happen back-to-back for the same file; throttled to at most ~20 updates regardless of suite size (a count-based gate, not a timer), so this never floods a non-TTY log.
- **`Checking cache...`** once, immediately before per-item dispatch begins, only when content-addressed caching is actually enabled for this run (a store, a run id, and a cache-key port all present) — otherwise nothing would be checked, and this line never appears.

Rendered the same way the per-item checkpoints above are: a single redrawn `\r` line on a TTY (closed with a trailing `\n` once dispatch's own progress line takes over, or once the run turns out to have nothing to dispatch at all), one `\n`-terminated line per milestone off one. **`--evaluate` only** — `--dry-run` and the plain default report run through the identical discovery/extraction/evidence pipeline, but neither wires a progress port at all today, so neither prints these lines; `stdout`/`--json` output is byte-for-byte unaffected either way, since all of this stays on stderr.

Production wiring binds this to the real `process.stderr.write`/`process.stderr.isTTY`; `createTerminalProgressReporter` (`src/adapters/terminal-progress-reporter.ts`) is the adapter, `AuditProgressPort` (`src/domain/audit.ts`) is the port the domain and application layers see, and `CliDependencies.createProgressPort` is the test seam.

## Canonical JSON report (`audit --evaluate --json`)

`--evaluate --json` prints one versioned, self-describing JSON report — the tool's single canonical machine-readable output contract (Phase 6, task P6-2), built by the pure domain function `buildAuditReport` (`src/domain/report.ts`) and published as `docs/report-schema.json`. It replaces the pre-Phase-6 ad-hoc envelope with a stable, deterministic key order (proven by golden tests).

- **`reportVersion`** is this envelope's own contract number — currently `1` — independent of `versions.storeSchema` (the persistence layer's own schema version, currently `4`), `versions.rubric`/`versions.policy` (this build's currently active rubric/policy pins), and each classification's own `rubricVersion`/`policyVersion` (a cached judgment is re-classified under the active policy, so its `policyVersion` matches the active pin; the fields are still reported per classification rather than inferred). The four never collide, and none of them is inferred from another.
- **`runId`** (Phase 6, task P6-2b) identifies the persisted run this report came from — the same id `audit --evaluate --resume <runId>` reads back, and the same id `--evaluate`'s terminal report already prints for a resumed run. Present for any run with a store: a fresh run's own newly minted id, or a resumed run's continued one (which always matches `resume.runId` below). Absent entirely — never a fabricated placeholder — when there is no persisted run to name: no `--evaluate`, no store wired, or evaluation never started at all. This is what lets a report be traced back to the store it came from without a separate run-lookup table; see "Audit store" below.
- **`complete`** is `false` only when this run's evaluation never ran at all — in practice, when discovery failed before evaluation could start (`incompleteReason` then names the diagnostic). It is `true` for a run with failed test cases, skipped test cases, a model-pin mismatch, or a `needs-review` verdict: those are ordinary, fully-disclosed per-test outcomes already carried in `totals`/`classifications`/`diagnostics`, never confused with a truncated run. No finding and no infrastructure failure changes the exit status either way (see "Jev evaluation" above) — an incomplete run still exits `0`.
- **`discovery`** exposes the same discovery decisions the default (non-`--evaluate`) summary does: which files were found, their framework and test-case counts, which files were excluded and why, and the aggregate `AuditTotals`.
- **`totals`** is the run-level evaluation summary (evaluated/cached/failed/skipped counts, usage, status counts, responded model, model mismatches) — unchanged in shape from the pre-Phase-6 report.
- **`latency`** aggregates wall-clock latency (Phase 6, task P6-1) across every test case with a measured fresh-dispatch latency this run — `measuredTestCases` plus `totalMs`/`meanMs`/`minMs`/`maxMs`, the four present only when something was actually measured (never a fabricated `0`).
- **`cacheStatus`** lists every evaluable test case exactly once with its cache provenance — `cached` (served from the content-addressed cache), `fresh` (a genuinely new provider request this run), or `not-evaluated` (dispatched but the request failed). A skipped test case never appears here — caching is not a meaningful question for it.
- **`classifications`** carries the same per-test shape as before (dimension judgments, probabilities, findings, model, usage, evidence provenance) plus two additions: `cache` (`cached`/`fresh`, mirroring `cacheStatus`) and, when measured, `latency` (`latencyMs`/`attemptLatenciesMs`). `evidence` now also carries the full `denied`/`unresolved`/`omitted` decision lists (rule/specifier/reason), not only their counts — fragment *content* itself is still never included.
- **`diagnostics`** and, when resuming, **`resume`** are unchanged from before.

Schema validation has no extra runtime dependency: `docs/report-schema.json` is validated in this project's own test suite by a small hand-rolled structural validator (`src/domain/report-schema.ts`), never a third-party JSON Schema library. The package's runtime dependency is `typescript`, imported by `dist/` to parse source with the compiler API.

## Self-contained HTML report: a fixed-size overview (`audit --evaluate --html [path]`)

`--html [path]` (Phase 6, task P6-4; rewritten as a fixed-size VISUAL OVERVIEW by `odd/tasks/html-report-overview.md`) renders the run `--evaluate --json` reports on into one offline HTML file at `[path]` (default: `report.html` in the invocation directory) — a pure function (`renderAuditReportHtml`, `src/domain/html-report.ts`) over the already-built `AuditReport`, with no I/O, no timers, and no adapter imports of its own. **Without this flag, no file is written at the invocation directory.** This preserved Phase 5's "nothing is written unless explicitly asked for" guarantee for every surface that writes a file at a location the caller names — that guarantee now has one deliberate, disclosed exception: every `--evaluate` run, with or without `--html`, also persists its canonical report inside the *audited project's own root* (`<rootDir>/.jta/`, never the invocation directory) — see "Persisted run reports" below.

- **Default path.** `--html` with no path (end of the arguments, or followed by another option such as `--open`) writes `report.html` into the directory the command was invoked from — not `--rootDir` — overwriting it on every run. `report.html` is git-ignored in this repository.
- **An overview, not a per-test listing.** A real run's page must stay a fixed size regardless of whether it judged 20 tests or 20,000, so the page never renders one row, block, or `<details>` per test case, per file, or per diagnostic. It renders a small, fixed set of aggregates instead (`summarizeReport`, `src/domain/report-overview.ts`): a headline "X% of N judged tests need a change" counting misleading/weak tests only (a percentage, not a bare count — "3,757 of 7,200" reads as ">50%") with a visually secondary "needs review" figure right below it, over the same judged denominator, for the share that is merely uncertain (`needs-review` — never folded into the headline, since it is not a confirmed defect), a status-share bar (misleading/weak/needs-review/healthy, worst first, direct-labeled with count and percent), per-dimension diverging bars (misleading/weak on one side, acceptable/strong on the other, worst dimension first; needs-review/not-applicable counted separately), a folder x dimension heatmap (the share of each folder's own applicable tests that are misleading or weak, per dimension; folders drill down adaptively — big enough to be worth resolving further splits into modules/features, e.g. `backend/src/modules/budgets`, never stopping at a bare `backend/src` row — capped at 12 folders plus one trailing "Other" row), a top-10 file ranking by tests needing a change (misleading/weak only), run coverage (discovered → judged, cached/failed/not-evaluated/skipped counts), and diagnostics grouped by code (never one row per diagnostic). Every percentage states its own denominator, and a share with a genuinely empty population never renders as a misleading `0%` (or `NaN`) — it reads `n/a` instead.
- **Per-test detail lives only in `--evaluate --json`.** Dimension scores, findings, and evidence provenance for one specific test case are not reachable from the HTML page at all — this is the one deliberate trade the overview makes, so the file stays a glance rather than a document.
- **No embedded canonical JSON.** An earlier version of this page also embedded the full canonical report verbatim as inert JSON data; a real 7,234-test run made that file weigh megabytes, so the report no longer carries it (user decision, 2026-09-23) — the HTML is for a glance, `--evaluate --json` is the machine-readable source of truth.
- **Genuinely self-contained, with zero `<script>` tags.** Every style is embedded inline; there is no `<link>`, no `@import`, no external stylesheet or font, no CDN, and no network call at render or view time — the file works on a machine with no internet. Every chart is server-rendered inline HTML/CSS (flex-grow-sized bars for the status/dimension charts, the palette's own neutrals for the heatmap/top-files magnitude, with ember reserved for hotspots at or above 50% misleading or weak), and every mark carries a native `title="…"` attribute naming its exact value and denominator for hover — there is no client script at all, since the old text filter/expand-all behavior went away with the per-test list it operated on. Proven in this project's own test suite by a category-based scan (absence of the whole class of external-reference constructs — protocol-relative URLs, `<iframe>`/`<embed>`/`<object>`, any `<script>` tag at all, `@import`/`url(…)` inside a real `<style>` block), not by grepping for a couple of known-bad substrings.
- **Escaping.** Every value written into the page — a folder name, a file path, a dimension label, a persisted diagnostic code or message, any of which can contain `<`, `&`, quotes, or a literal `</script>` sequence — is HTML-escaped before it is placed in the page, proven with genuinely hostile payloads (`</script><script>…`, `"><img src=x onerror=1>`), not a polite `<b>` tag.
- **Renders from the report alone.** The renderer never touches the filesystem, the audit store, or the audited repository — it is possible, and tested, to render the page from an `AuditReport` with no repository and no database present at all.
- **Overwrite.** An existing regular file at `<path>` is silently overwritten (the established convention for an explicitly named output path — this project's own `auth login` already overwrites a stale stored credentials file the same way); the overwrite is still disclosed on stderr. An existing directory at `<path>`, or a path whose parent directory does not exist, is a usage error (exit 1, readable message, no stack trace) reported **before** any evaluation work is dispatched, so a bad path never costs a real request. No parent directory is ever auto-created.
- **`--open`** launches the file in the OS default viewer once it is written — `open` on macOS, `xdg-open` on Linux, `explorer.exe` on Windows — detached, never blocking the CLI on the viewer closing. A failed launch (most commonly: no viewer installed, the ordinary case in CI) is reported on stderr only and never changes the exit status or touches the already-written file.
- **Both go to stderr, never stdout.** The write confirmation (and, on `--open`, any launch failure) is written to stderr, exactly like progress (P6-3) — `--evaluate --json`'s stdout stays byte-clean, exactly one canonical JSON line, regardless of whether `--html`/`--open` were also given.

## Persisted run reports (`.jta/`) and `jta report`

Feature `odd/tasks/persisted-run-reports.md` (2026-09-23). Until now, the canonical report only ever existed on stdout (`--evaluate --json`) or as a self-contained HTML file at whatever path `--html` named — once a run finished, nothing an agent (or a later `jta` invocation) could read remained, short of re-running `--evaluate` itself (which needs an API key and re-bills failed test cases). This closes that gap: every `--evaluate` run leaves its complete canonical JSON report on disk in the *audited project itself*, and the read-only `jta report` command prints or re-renders it without ever re-evaluating anything.

- **Where, and when.** Every `audit --evaluate` run — with or without `--json`/`--html` — writes the exact same canonical `AuditReport` JSON `--evaluate --json` would print (byte-identical, the very same string, never a re-derived copy) to two places inside `<rootDir>/.jta/`, the *audited project's own root* — deliberately not this tool's per-user config directory (`~/.config/jev-test-auditor`, where the SQLite audit store and the stored API key live): `.jta/reports/<runId>.json` (one file per run) and `.jta/latest.json` (a copy of the run that just finished, so a reader never has to know a run id at all).
- **Self-ignoring.** `.jta/.gitignore`, containing a single `*`, is created the first time `.jta/` is created — so the folder never gets committed, without touching the project's own `.gitignore`. An existing `.jta/.gitignore` (including a hand edit) is never overwritten.
- **`.jta` is a default-excluded discovery path**, exactly like `.git`/`node_modules`/`vendor` — a repeat `--evaluate` run over the same project never discovers its own prior output as an ordinary excluded file.
- **Retention: the 5 most recent runs.** Once a write pushes `.jta/reports/` past 5 files, the oldest are deleted — ordered by each file's own filesystem modification time (`runId` is a random UUID, not time-ordered, and the canonical report carries no timestamp of its own, so recorded time is the only deterministic signal available; see `src/domain/report-retention.ts`). The report a call just wrote is never itself a deletion candidate.
- **Never fails the audit.** A persistence write failure (permission denied, disk full, `.jta` blocked by a same-named file, …) is reported as one line on stderr and never changes `--evaluate`'s own exit code or stdout — exactly like a failed `--open` launch above. `--evaluate --json`'s stdout stays byte-for-byte what it always was.
- **`jta report [--last | --run <runId>] [--json | --html [path]] [--open] [--rootDir <dir>]`** reads back what was just persisted — no API key, no network, no audit store access, and it never dispatches a new evaluation:
  - **Which run**: `--last` (the default, even with neither flag given) reads `.jta/latest.json`; `--run <runId>` reads `.jta/reports/<runId>.json` specifically. Mutually exclusive.
  - **Output shape**: `--json` prints the stored JSON exactly, byte-identical to that run's own `--evaluate --json` stdout. `--html [path]` renders the identical fixed-size offline overview `audit --evaluate --html` does (same renderer, same default `report.html`, same overwrite/preflight/`--open` rules). Neither flag prints a short human summary instead: the run id and recorded time (that file's own modification time), the headline "needs a change" share and its denominator (misleading/weak only), a separate "needs review" share over the same denominator, and the worst folders by tests needing a change (reusing `summarizeReport`, the same aggregation the HTML overview is built from). `--json` and `--html` are mutually exclusive; `--open` requires `--html`.
  - **`--rootDir <dir>`** reads `<dir>/.jta/` instead of the current directory — the same audited-project root `--rootDir` names for `audit`.
  - **Errors are exit 1 with a clear, actionable message**: no `.jta/` or no persisted reports yet (suggests `jta audit --evaluate`); `--run <runId>` naming a run id that does not exist (lists every id that *is* available); the stored JSON is unreadable (invalid JSON) or fails the same schema `docs/report-schema.json` publishes for `--evaluate --json` — validated with the existing hand-rolled structural validator (`validateAgainstSchema`, `src/domain/report-schema.ts`), now also exercised at CLI runtime, not only in this project's own test suite.

## Agent skill (`skills/jev-test-audit`)

`jev-test-auditor` stays CLI-only and reporting-only (see "Product boundaries" below) — it never edits a test file itself. `skills/jev-test-audit` is the agent-facing counterpart: a skill directory (`SKILL.md`, a small `assets/` folder, and a `references/` folder) a coding agent (Claude Code, or any agent runtime that loads `SKILL.md` files) loads to read a persisted report, explain it in plain language, and — only with your explicit, per-batch approval — dispatch one fix subagent per test file and verify the result.

- **What it does.** Reads the latest report via `jta report --last --json` and queries it through the bundled zero-dependency `assets/report-query.mjs` (a real audit can be several MB of JSON — the skill never loads the full report into the agent's context). That script is a subcommand tool, not just one summary: `summary`, `worklist`, `file <path>`, `test <name>`, `folders`, `dimensions`, `batches`, `diff`, and `runs` (`--help` lists them all), so the agent has a script for every question it needs to ask instead of guessing from raw JSON. It explains the "needs a change" share, its denominator, and which folders/dimensions are worst (`references/dimensions.md` gives the plain-language meaning of each), then proposes a fix plan in batches (by file or folder) and waits for you to say which to fix. Each approved file gets its own fix subagent, briefed with `assets/fixer-brief.md`: edit that one test file only, never production code, never weaken or delete an assertion (or add a `.skip`) just to make it pass, and stop and report back — instead of guessing — when a real fix would need a production change or a product decision. After fixes land, it runs your test command and can offer a consented re-audit, then `diff` the before/after.
- **Install.** Copy the `skills/jev-test-audit` directory into your agent's skills directory, for the project you're auditing — for Claude Code, `~/.claude/skills/jev-test-audit` (every project) or `<your-project>/.claude/skills/jev-test-audit` (that project only). Find the source directory to copy: `npm i -g jev-test-auditor` installs it under `$(npm root -g)/jev-test-auditor/skills/jev-test-audit`; a project-local `npm i jev-test-auditor` under `node_modules/jev-test-auditor/skills/jev-test-audit`. No build step; `assets/report-query.mjs` runs as-is with plain `node`.
- **Approval rule.** The skill never edits a test file without your explicit approval of that specific batch, and a fix subagent never touches production code. `jta audit --evaluate` itself is never run without your explicit consent either — see the cost note next.
- **Cost note.** Reading a persisted report (`jta report`) is free and always offline. Producing a *new* one (`jta audit --evaluate`) calls TypeSafe's Jev model and costs money, and unchanged tests are cached so a re-audit after fixes only bills the files that actually changed — the skill will suggest `jta audit --dry-run` first so you see the estimated cost, and only runs `--evaluate` with your explicit go-ahead.

## Audit store (SQLite persistence)

`audit --evaluate` persists every terminal work-item outcome to a local, per-user SQLite database, in addition to printing the evaluation report: runs, work items and their terminal states, attempts (raw answers and token usage), normalized judgments, errors, and skips. **The API key never reaches the database.**

- **Strictly opt-in to CREATE.** An audit without `--evaluate` never creates a database file or config directory — the writable store is only constructed after a usable API key has already resolved, exactly like the evaluation port it is gated behind. `audit --dry-run` is the one exception that may READ an already-existing store (to report cache hits — see "Dry-run cost and call estimate" below), but it opens that store strictly read-only (a `file:` URI carrying `mode=ro`, plus `readOnly: true`) and never creates the store, migrates it, or writes any of its data; with no store yet at the configured path, `--dry-run` never even attempts to open one, so it remains exactly as side-effect-free as before this read path existed. It may, however, leave a `-wal`/`-shm` sidecar file next to a WAL-mode store — see "The read-only guarantee" under "Dry-run cost and call estimate" below.
- **Storage location**: the same per-user config home convention as the stored API key (see "Local API key storage" above) — POSIX: `$XDG_CONFIG_HOME/jev-test-auditor`, or `~/.config/jev-test-auditor` when unset; Windows: `%APPDATA%\jev-test-auditor` — under its own `audit-store.sqlite3` file (so it never collides with `credentials.json`), inside a directory created owner-only (`0o700` on POSIX; Windows does not enforce this, same as the credentials directory above). Overridable with the `store.databasePath` configuration key (`store: { databasePath: '/custom/path.sqlite3' }`), the same override pattern as `evidence: { maxFragmentBytes, maxBundleBytes }` below.
- **Append-only.** No run, work item, attempt, judgment, error, or skip record is ever updated or deleted once written — history accumulates across every `--evaluate` run. The one exception is a run's own `finished_at` marker, set once when that run completes; it never rewrites a fact already recorded about a test case.
- **Every work item's intended state is durable, not only its finished state.** Before the scheduler dispatches anything, every evaluable item gets a `pending` checkpoint; the moment the scheduler picks it up, it gets a `running` checkpoint; then its terminal outcome once it settles. A process killed mid-run leaves a readable trail of exactly how far each item got — `audit --evaluate --resume <runId>` reads that trail back; see "Resume" below.
- **No separate `reports` table.** A run's persisted identity travels with the canonical JSON report itself, as its top-level `runId` (Phase 6, task P6-2b — see "Canonical JSON report" above), the same id this store's own `runs` table recorded it under. That is the whole answer to looking a report up again later: nothing consults a run by id except `--resume`, which already reads this same store directly, so no manifest table of past reports is built.

## Content-addressed caching (`--fresh`)

Before dispatching a real request, `audit --evaluate` computes a content-addressed cache key for each evaluable test case and looks it up in the audit store. A hit reuses the stored raw Jev answers at zero cost and re-derives the classification from them locally under the current policy, recorded as its own `cached` work item; a miss dispatches a real request exactly as before, and the new judgment is recorded with that key so a later run can find it.

- **What the key covers.** The key is `sha256` over: the exact canonical Jev request bytes (`canonicalizeJevRequest`'s `{ state, model, questions }` — this already includes the pinned model id, every rubric question's wording, and the evidence bundle's selected fragments/denials/omissions), the normalized full test-file source (not only the fragments evidence selection happened to choose — an edit anywhere else in the file still invalidates), and the rubric's own numeric version. Changing any one of these inputs forces a new request; the model id and evidence-fragment invalidation come for free from the canonical request bytes, since the model id is `request.model` and a changed fragment changes `state.fragments` directly.
- **The classification policy is not part of the key.** The policy never reaches Jev — it runs locally over the returned answers — so a cache hit re-classifies the stored raw answers under the policy this build ships, and a policy change (for example recalibrated thresholds) never causes a provider request. The key payload still carries a `policyVersion` field frozen at `2` (`LEGACY_POLICY_VERSION_SLOT`), the value every store written before this change hashed, so existing cache entries stay hits instead of re-billing a whole suite once.
- **The key never depends on `rootDir`.** The same repository content audited from two different absolute paths produces the same key — Phase 3's provenance is already repository-relative, and the cache key inherits that.
- **When one key has several stored judgments** (append-only plus `--fresh` can accumulate more than one over time), a lookup returns the most recent `completed` judgment whose responded model still matches the pin; a pin-mismatched judgment is skipped in favor of an older matching one, and a key with no pin-matching judgment at all is a miss.
- **The lookup stays fast as the store grows (T2, `odd/tasks/audit-run-responsiveness.md`, schema version 4).** The lookup query joins `work_items`, `attempts`, and `judgments` on `work_item_id`; through schema 3, only `work_items.cache_key` was indexed, so every lookup paid a full scan of `attempts` plus an ad hoc index SQLite built and discarded on `judgments` on every single call — confirmed against a real ~8,700/14,900-row store (`EXPLAIN QUERY PLAN`: `SCAN a` plus `AUTOMATIC COVERING INDEX` on `j`), and the reason a warm, almost-entirely-cached run got slower with every lookup rather than faster. Schema 4 adds `idx_attempts_work_item_id`/`idx_judgments_work_item_id`, turning both joins into a plain indexed `SEARCH`; an existing store is upgraded to schema 4 automatically the next time `--evaluate` opens it (never by `--dry-run`, which only ever reads — see "The read-only guarantee" below).
- **`--fresh`** bypasses the lookup only — it never skips recording, so a fresh dispatch's result is still appended as a new, immutable judgment. It never mutates or deletes anything already stored under that key.
- **Reporting.** `audit --evaluate`'s terminal and `--json` reports add a `Cached`/`cached` count alongside `Evaluated`/`evaluated`: a cache hit still contributes its classification to `statusCounts`/findings exactly like a fresh success (both are valid, already-judged verdicts), but its token usage is excluded from the run's `usage` totals, since a hit spends nothing this run.
- **The `uncertain` work-item state** (in the schema's `CHECK` constraint and the `WorkItemState` type) is not produced by anything in this codebase as of this phase — it exists purely for forward compatibility, not as an active cache-lookup outcome.
- **`audit --dry-run` consults this same cache, read-only** (task P5-5): before estimating, it computes the identical key (`AuditCacheKeyPort.computeKey`) and looks it up (`AuditStorePort.lookup`) for every evaluable test case, through a read-only store connection — see "Dry-run cost and call estimate" below for exactly what that changes in the report and "Audit store" above for the read-only guarantee itself.

## Adaptive scheduling and resilience

`audit --evaluate` dispatches through an adaptive scheduler, not a fixed-size pool: it starts at configuration's `concurrency` (default 4) and adjusts automatically from what the provider actually does, never guessing from elapsed time.

- **Reduces on throttling, restores after a clean window, never above the ceiling.** A successful evaluation that needed the gateway's own internal retries (`attempts > 1` — see "Jev evaluation" above; the gateway retries only on HTTP 429/529) or an evaluation that ultimately failed with a rate-limit/overloaded error halves the effective concurrency (floored, never below 1). Five consecutive dispatches with no throttling signal at all restore it by one step, up to the configured `concurrency` again. A cache hit, or a failure of any other kind (auth, malformed response, timeout, abort), is neither — it changes nothing, so an unrelated failure never gets mistaken for either "the provider is throttling us" or "traffic is clean."
- **The gateway's own retry is untouched.** The scheduler wraps the outer dispatch loop only; per-call timeout, abort, and 429/529 backoff honoring `retry-after` still live entirely in `src/adapters/jev-http-gateway.ts`, exactly as before.
- **Observes the verified provider budgets**: 1,200 requests/minute and 250,000 tokens/second (`JEV_VERIFIED_RATE_LIMITS`), configurable via `schedule: { requestsPerMinute, tokensPerSecond }` for a library consumer (same pattern as `store.databasePath` — no CLI flag). A dispatch that would exceed either rolling window waits until it clears, independent of concurrency.

## Resume (`--resume <runId>`)

`audit --evaluate --resume <runId>` continues a previously started run instead of starting a new one. It reads the run's durable `pending`/`running`/terminal trail (see "Audit store" above), reloads every already-terminal work item (`completed`, `cached`, `failed`, or `skipped`) as-is, and dispatches only the items that are still outstanding — anything with no recorded row at all, or whose last recorded row is `pending` or `running`. An already-terminal item is never re-looked-up in the cache and never re-dispatched to the provider, regardless of how it originally resolved (including `failed`: a failure is a real, final outcome for that attempt, not something resume silently retries).

- **Same final report as an uninterrupted run.** The terminal report (`--evaluate`/`--evaluate --json`) combines the reused items with the freshly dispatched ones into the exact same totals, classifications, and diagnostics an uninterrupted run over the same fixture would have produced — a reused `completed` item still counts toward `Evaluated`/`usage`, a reused `cached` item still counts toward `Cached`, and a reused `failed` item still produces its original `evaluation-failed` diagnostic, word for word. `--evaluate --json`'s output additionally carries a `resume: { runId, outstanding, reused }` field naming how many items were dispatched versus reused; the human-readable report prints the same as one extra summary line.
- **Re-billing risk — read this before relying on cost savings.** An item whose last recorded state was `running` when the process was interrupted may already have been answered by the provider before that answer was ever received or recorded — there is no way to know from here whether the original request completed. Resuming re-dispatches it anyway, since that is the only correct choice (its result was never durably recorded), so a resumed run can cost slightly more than the work it visibly appears to redo. This is unavoidable, not a bug: persistence only ever records a fact once it is fully known.
- **`--resume` and `--fresh` are orthogonal, and can be combined.** `--resume` decides *which* items run this invocation (only the outstanding ones); `--fresh` decides whether the items that *do* run consult the cache first. Combining them dispatches a fresh request for every outstanding item, bypassing the cache for those only — an already-terminal reused item is untouched either way, since it was never a candidate for cache lookup or dispatch in the first place.
- **`--rootDir` is compared by repository identity, not spelling.** A run's `rootDir` is canonicalized (resolved to an absolute path, then symlinks followed) at the moment it is recorded, and a `--resume` request's `rootDir` is canonicalized the same way before comparing — so the same repository audited via a relative path, an absolute path, a path with a trailing slash, or a symlinked ancestor directory all resume the same run. Canonicalization happens once, when the value is persisted or freshly supplied; a raw stored value is never re-interpreted later, because doing that would resolve it against the wrong (resume-time) working directory instead of the one the original run actually audited.
- **Named, visible failure modes — never a silent fresh start.**
  - A run id that does not exist in the audit store: usage error, exit 1.
  - A run id recorded against a genuinely different repository than the one being audited now: usage error, exit 1, naming both roots.
  - A run recorded by a version of this tool before it canonicalized `rootDir` (its stored root is not an absolute path — most commonly the "." default from an audit that predates this fix): usage error, exit 1, naming the recorded root. It cannot be safely resumed at all, because there is no way to tell which repository its raw, uninterpreted root string ever meant — re-run the audit without `--resume` to start fresh.
  - A run that is already finished with nothing outstanding: **not an error** — reported honestly (`Nothing to resume: run <runId> has no outstanding work items.`), exit 0, and nothing is dispatched.
- **Requires `--evaluate`** (and, transitively, a working audit store); `--resume` alone is a usage error.
- **A currently evaluable item that was recorded `skipped` before the interruption** (e.g. a `.skip` modifier was removed from the source since) is treated as outstanding and genuinely dispatched, never silently miscounted — resume assumes the audited repository is unchanged since the interrupted attempt, and degrades safely rather than losing coverage when that assumption does not hold.

## Classification policy

Each rubric dimension is judged independently, then combined into one non-compensatory verdict per test: `healthy`, `weak`, `misleading`, or `needs-review`. The verdict only ever depends on a single boundary — deficient (`misleading`/`weak`) versus acceptable (`acceptable`/`strong`) — and any judged `misleading` dimension forces the whole test `misleading` regardless of what else scored well; a strong dimension never cancels a critical failure elsewhere.

As of `odd/tasks/classification-calibration.md` task C-1, a dimension's level is decided from the quality answer's probability distribution across its four levels, not from `confidence` or the weighted `score` alone. For each applicable dimension the tool computes:

- `deficientMass` — the probability on `misleading` + `weak`.
- `acceptableMass` — the probability on `acceptable` + `strong`.
- `criticalMass` — the probability on `misleading` alone.

A dimension is deficient when `deficientMass` clears `sideMin` (0.65) and acceptable when `acceptableMass` does; a deficient dimension is reported `misleading` only when `criticalMass` also clears `criticalMin` (0.5), otherwise `weak`. `needs-review` at the dimension level now means the mass genuinely straddles that one boundary — not that the answer merely leaned toward two adjacent levels on the same side of it, which is what the earlier `confidence`-based gate mistook for uncertainty.

`score` and `confidence` are still reported on every dimension for transparency and audit — the full `probabilities`/`deficientMass`/`acceptableMass`/`criticalMass` breakdown appears in `--evaluate --json` — but neither is consulted to decide a level any more. That means a dimension can show a `score` under 2 (nominally "weak" by the old cut points) and still be reported `acceptable`: on the recorded pr-hero run below, one dimension scored 1.97 with a distribution of `{weak: 0.06, acceptable: 0.91, strong: 0.03}` — 94% of the mass on acceptable-or-better — and was correctly reported `acceptable`. A sub-2 score on a `healthy` test is not a bug; it means the model leaned decisively toward one side even though its weighted mean happened to sit near the old boundary.

This is `CLASSIFICATION_POLICY_V2`, paired with `RUBRIC_V2` (task C-2, which rewrote the `determinism-isolation` and `falsifiability` applicability questions so they ask whether the shown evidence supports a judgment, not whether every possible influence is visible — the two dimensions were excluding themselves on tests Jev could actually judge). Both are what the shipped `--evaluate` path uses; `CLASSIFICATION_POLICY_V1` and `RUBRIC_V1` remain exported only to replay real provider output recorded before this change.

**Thresholds remain provisional and versioned, not calibrated claims.** `applicabilityMin` (0.5), `sideMin` (0.65), and `criticalMin` (0.5) were picked mid-gap from ranges observed in one recorded run, not fit to a validated outcome; Phase 7 ("Benchmarks and calibration") is what calibrates them, and any recalibration ships as a new policy version, never a silent edit.

## Dry-run cost and call estimate

`audit --dry-run` (and `--dry-run --json`) previews the aggregate Jev calls and cost an audit would make, without ever calling Jev, requiring an API key, or writing anything to disk. It runs the exact same no-network, no-write discovery/extraction/evidence pipeline as a normal audit, then reports:

The plain `audit` default (see "Current CLI" above) folds this exact same estimate into its own report — same computation, same read-only cache consultation, same wording. `--dry-run` on its own stays the focused, estimate-only view: just this section's numbers, nothing about discovered/excluded files or diagnostics, and (with `--json`) a stable machine-readable shape scripts can parse without picking through the fuller default report.

- **Exact**: discovered test-case count; `evaluable` count and `skipped` count broken down by reason (`skip`, `todo`, `evidence-unavailable` — no evidence bundle was built for that test case); `initialCalls` (one Jev call per evaluable test case that is not already served from the local content-addressed cache — task P5-5; equal to `evaluable` when no audit store was found to consult, exactly as before that task); `evidenceBytes` (the exact sum of `canonicalizeEvidenceBundle` UTF-8 byte lengths over every evaluable bundle — the local evidence footprint, kept for its own sake); `requestBytes` (the exact sum of `canonicalizeJevRequest(buildJevRequest({testCase, bundle, rubric}))` UTF-8 byte lengths over every evaluable test case — the actual request Jev would receive, `state` plus every rubric question); `rubricBytesPerRequest` (the exact byte length of just the rubric's own `questions` map, the same for every request under a given rubric, independent of test-case count — this is what makes `requestBytes` so much larger than `evidenceBytes`). A conditional `skipIf`/`runIf` modifier counts as evaluable — it is a runtime condition, not a statically known skip. `evidenceBytes`/`requestBytes`/`rubricBytesPerRequest`/`bundlesOverCeiling` stay scoped to every evaluable test case regardless of caching — they describe the discovered work itself, not what would be billed for it.
- **Cache-aware billing (task P5-5).** If an audit store already exists (default or `store.databasePath`-configured location) and is at this build's current schema, it is opened strictly read-only and consulted for each evaluable test case's real content-addressed cache key, the identical key and lookup a real `--evaluate` dispatch would use. A hit is excluded from `initialCalls` and the token/cost estimates below and counted instead in `cacheHits` (present, even as `0`, only when the cache was actually consulted). The billable count this reports is guaranteed to equal what a subsequent real `--evaluate` run over the same fixture and store actually dispatches, because both paths call the exact same `AuditCacheKeyPort.computeKey` and `AuditStorePort.lookup` functions on the exact same inputs.
- **Cache-consultation disclosure (orchestrator decision, 2026-09-20).** Whether the cache was consulted at all is always reported explicitly — `cacheConsulted: true`/`false` in JSON; in text, a consulted preview keeps saying so exactly as before (the `Cache hits` line already covers it, unchanged). When `cacheConsulted` is `false`, the reason is named too (`cacheNotConsultedReason`; text: a `Cache: not consulted (...)` line), distinguishing the two known cases: `no-store` (no audit store exists yet at the configured location — nothing to consult), and `schema-outdated` (a store exists, but its recorded schema predates this build; a dry run must never migrate it, so the reason line points at `--evaluate`, which upgrades the store on its own next write). This makes "consulted, zero hits" discoverable without inferring it from a missing `cacheHits` key, and turns a silent "why wasn't this cached" into an explicit, machine-readable answer. A store newer than this build, or one `readSchemaVersion` rejects as corrupt/foreign, is unaffected by this disclosure — it still fails with the same named, visible error (`AuditStoreSchemaVersionError`/`AuditStoreCorruptError`, exit 1, no stack trace) a real `--evaluate` against the same file would also raise; see "The read-only guarantee" below.
- **The read-only guarantee holds even when a store exists — including a store another `--evaluate` process is writing to right now (T1, `odd/tasks/audit-run-responsiveness.md`).** `--dry-run` never creates the store, never migrates it, and never writes a single byte of its actual data — verified empirically (not merely asserted) by hashing the store file before and after a warm dry run and confirming byte-for-byte equality. This opens the file through a `file:` URI carrying `mode=ro` together with `{ readOnly: true }` — the standard way to open a WAL-mode SQLite database read-only, so this reader participates in the same locking/wal-index protocol every other connection does and always sees the current, consistent, committed state, including a row still sitting only in an uncheckpointed `-wal` sidecar (a concurrent `--evaluate` run that has not checkpointed yet). An earlier version of this reader used `immutable=1` instead, on the theory that the file "would not change" during the read; against a genuinely concurrent writer that promise does not hold, and the failure ranged from an honest but silent undercount (a committed-but-not-yet-checkpointed row simply invisible) to a hard crash (`database disk image is malformed`) — `mode=ro` fixes both. The one tradeoff: `mode=ro` against a WAL-mode store (every store this tool creates) may itself create or refresh a `-wal`/`-shm` sidecar file, which a read-only connection cannot always clean up on close — harmless WAL coordination metadata, never written data, reused or checkpointed away by the store's own next writable open.
- **A possible range, exactly bounded**: `followUpCalls` (`0` to the billable count `* maxFollowUpsPerTest`) — a follow-up call happens only when an earlier Jev result identifies a specific evidence need, never an automatic retry, so the true count is unknown ahead of time but its upper bound is exact.
- **Clearly labeled approximate**: `estimatedInputTokens`, `estimatedFollowUpInputTokens`, and `estimatedUsd` ranges, converted from the billable subset's `requestBytes` (not `evidenceBytes`) through a versioned local `bytesPerToken`/`usdPerMillionInputTokens` pricing snapshot (`JEV_ESTIMATE_SNAPSHOT` in `src/domain/estimate.ts`; the exact pinned model `jev-1.13.0`, USD 0.042 per 1,000,000 input tokens, output tokens unbilled, as of 2026-09-20). `bytesPerToken` (`3.0`–`4.8`) is calibrated from the first real Jev run's measured ratio of 4.458 bytes/token (320,360 canonical request bytes / 71,855 billed input tokens across 11 requests) — provisional, from one real run of English/TypeScript content, not a broad statistical sample. The bounds are deliberately asymmetric: a ratio above `max` only overestimates cost (harmless), but a ratio below `min` would understate what is actually billed, so `min` is set well below the single observed sample rather than tight around it — JSON-heavy or non-Latin/CJK evidence can tokenize below even this floor, a known current limit. `bundlesOverCeiling` counts evaluable test cases whose own real request's worst-case tokens would exceed the provider's 64k-token request ceiling (expected `0` under the current evidence budgets).
- **No more guessed overhead.** A previous version of this estimator added a guessed `requestOverheadTokens` range (620–2,440 tokens) on top of evidence bytes to stand in for the rubric's cost. The first real run showed that guess was wrong by roughly 2.5x (the rubric alone costs ~5,900 tokens per request) and unnecessary — the rubric is in the repository, so `--dry-run` now builds the real request and measures it instead of guessing. `requestOverheadTokens` no longer exists on `JEV_ESTIMATE_SNAPSHOT`.
- `audit --evaluate` (see below) sends this exact same request and reports exact usage from the provider's own response.

## Evidence bundles

- **Budgets**: each fragment is capped at `maxFragmentBytes` (default 4 KiB) and each bundle at `maxBundleBytes` (default 16 KiB), overridable through configuration (`evidence: { maxFragmentBytes, maxBundleBytes }`); values are provisional until later calibration. A fragment that would overflow is truncated at the last fitting line (falling back to a UTF-8-safe byte cut); a fragment that cannot fit at all is recorded as `omitted` rather than invented.
- **Deny list**: sensitive, generated, and vendor paths (`.env*`, `*.pem`, `*.key`, `**/node_modules/**`, `**/dist/**`, and more — see `DEFAULT_EVIDENCE_DENY_PATTERNS`) are denied *before* any read. Configuration (`evidence: { deny: [...] }`) adds patterns on top of these defaults; it can never remove or replace them.
- **Import depth**: direct imports of the test file (hop 1), plus one extra hop only through helper files (a test file, a file under `test`/`tests`/`__tests__`/`__mocks__`, or a file whose basename contains `helper`, `fixture`, or `setup`). Production files are never expanded further. A relative specifier resolves lexically; a non-relative specifier is checked against the importing file's own alias configuration first (see below) before falling back to `unresolved` (`bare-specifier`/`alias-specifier`).
- **Alias, subpath import, and workspace resolution**: a non-relative specifier is checked against the importing file's own statically declared configuration — read as text and never executed — before it is ever classified `bare-specifier`/`alias-specifier`. Three mechanisms are read, each from the **nearest** configuration above the importing file, not just the repository root:
  - **Node subpath `imports`** — the nearest `package.json`'s `imports` map, `#name`/`#name/*` keys only. A conditional value picks `default`, then `import`, then `node`; any other condition is recorded (`imports-unsupported-conditions`) rather than guessed at.
  - **TypeScript/JavaScript `paths` and `baseUrl`** — `tsconfig.json`/`jsconfig.json` `compilerOptions.paths`, following in-root `extends` chains (`tsconfig.json` wins over `jsconfig.json` at the same directory level; a nearer directory always wins over a farther one). `paths` targets resolve relative to the effective `baseUrl`'s directory when one exists anywhere in the chain, matching TypeScript's own rule, or relative to the directory of whichever config declared `paths` when no `baseUrl` exists at all. An `extends` target outside the repository root or inside `node_modules` is refused and recorded, never followed; a cycle is caught and recorded, never recursed into. `baseUrl` alone (no `paths`) also acts as a bare `*` catch-all, applied last and only when nothing else matched — a `baseUrl`-only config never mislabels an ordinary npm import (e.g. `lodash`) as a stale alias, because an unmatched `baseUrl` catch-all does not produce `alias-mapped-not-found`.
  - **Workspace package names** — read once from the **root** `package.json`'s `workspaces` globs and each member package's own `name` (workspaces are root-only; the other two mechanisms use the nearest config). A bare package name prefers real source over generated output: `packageDir/src/index`, then the package directory's own top-level files, then the package's declared `exports['.']`/`main` entry — so a package whose declared entry is `dist` build output resolves to source when source exists, and is reported `denied` (never silently dropped) only when it does not. A `name/*` subpath maps straight to `dir/*`, without consulting `exports` subpaths other than `.`.

  Precedence when more than one mechanism could apply: `imports` → `paths` → `workspace` → `baseUrl`. Within one mechanism, TypeScript's own matching rule applies: an exact (star-less) pattern always beats a wildcard; among matching wildcards, the longest prefix wins, ties broken by declaration order; a pattern with two or more `*` never matches anything. A matched entry's targets are tried in declaration order, re-checking containment after wildcard substitution (the specifier's captured text is caller-controlled). Every resolved target — mapped or relative — still passes the same extension/index probing, deny list, and realpath containment described above, unchanged. A specifier matched by a declared `imports`/`paths`/workspace entry whose every target is missing is reported `alias-mapped-not-found`, distinguishing a stale mapping from a specifier no mechanism recognized. A hop-2 helper file's specifiers use the **helper's own** nearest configuration, never the test file's.

  **Not resolved**: bundler-specific aliases (webpack/vite `resolve.alias` and similar plugins), anything that would require executing project code or configuration, `node_modules` contents (including an `extends` target that resolves into `node_modules`, such as an npm-published base tsconfig), and `exports` conditional subpaths other than `.` on a workspace package. Separately, and unchanged from relative resolution: discovery itself still only finds `.test`/`.spec` JS/JSX/TS/TSX files, so the deferred `*_test.*`/`*_spec.*` filename patterns and extra test-file extensions bun also supports never reach resolution at all — that limit is about which test files are found, not which of a found file's imports resolve.

  **Known limitation.** When an alias-mapped specifier's first existing target is denied, resolves outside the repository root, or has an unsupported extension, resolution stops there — it does not fall through to try a later-precedence mechanism for the same specifier, even if one would have resolved differently. Checked on musive-s1, the only repository with denials: every denial is a workspace package's `dist` entry, and the only lower-precedence mechanism left to fall through to is `baseUrl` (`.` at each package's own directory) — no package tree contains a literal `@<scope>/<name>` subdirectory a `baseUrl` catch-all could ever have matched instead, so the divergence was inert here. It is not proven correct in general.

  **Measured effect**, re-measured independently 2026-09-20 against the same four repositories A-2 recorded, and matching A-2's numbers exactly in every cell: "before" ran `bd74fbd` (the commit immediately before alias resolution was wired into evidence resolution) built in a throwaway git worktree; "after" ran this branch's build (`audit --rootDir <repo>`):

  | Repository | Mechanism(s) present | Fragments / tests (before → after) | Fragments per test (before → after) | Unresolved (before → after) | Denied (before → after) |
  | --- | --- | --- | --- | --- | --- |
  | pr-hero | subpath `imports` | 5,188/3,597 → 8,372/3,597 | 1.44 → 2.33 | 17,316 → 7,665 | 0 → 0 |
  | supermarket-pro | tsconfig `paths`/`baseUrl` | 21,560/6,677 → 25,480/6,677 | 3.23 → 3.82 | 13,998 → 17,619 | 0 → 0 |
  | musive-s1 | workspaces + inherited `paths` | 12,773/6,828 → 16,993/6,828 | 1.87 → 2.49 | 48,136 → 18,282 | 3 → 4,035 |
  | jev-test-auditor (this repo, no aliases) | none | 1,505/552 → 1,505/552 | 2.73 → 2.73 | 1,294 → 1,294 | 0 → 0 |

  This is not a uniform win, and the unresolved count is not a quality metric on its own — it only reflects how much of the dependency graph became reachable. supermarket-pro's unresolved total **rose**: resolving `paths`/`baseUrl` makes previously-unreachable helper files reachable, and those helpers import their own real npm packages. Measured directly: `alias-specifier` fell from 1,165 to 0, while `bare-specifier` rose from 12,813 to 17,599 as the newly reachable helpers exposed those imports (12,813 + 1,165 + 20 `unsupported-extension` = 13,998 before; 17,599 + 0 + 20 = 17,619 after). musive-s1's denied count rose from 3 to 4,035 — verified as 4,032 `**/dist/**` refusals plus the 3 pre-existing `**/node_modules/**` ones — almost entirely the source-preference rule refusing a workspace package's prebuilt `dist` output once the workspace mechanism made that package reachable at all. The metric that matters is fragments per test: it rose in every repository with a resolvable mechanism, and did not move for this repository, which has none.
- **Failure isolation, two levels, never a placeholder bundle**: uncertainty is not quality, so a failure never produces an empty-but-structurally-valid bundle standing in for "this test genuinely has no supporting evidence." A whole-file failure (e.g. a helper read failing) is isolated to that file — one `evidence-failed` diagnostic naming the path, an empty `evidence` array for that file, every other file unaffected. A single test case's selection failing does not drop that file's other bundles, and produces no bundle of its own — only one `evidence-selection-failed` diagnostic naming that test case's id and name. Either way the diagnostic is merged into both the file's own diagnostics and the root `diagnostics` (with the file path attached), exactly like an extraction diagnostic. `evidenceBundleCount` and the evidence totals always reflect only the bundles that were actually built. Nothing here executes audited code, package scripts, test runners, or configuration modules.
- **Nothing is sent anywhere by default**: evidence selection is entirely local, and no network call is ever made unless `--evaluate` is explicitly passed. `src/` contains no raw network module import (no `node:http`/`node:https`/`node:net`/`node:tls`/`undici`) anywhere, and exactly one reviewed `fetch(...)` call site exists in the whole codebase — the TypeSafe HTTP gateway adapter used only by `--evaluate` — enforced by an architecture test alongside the inward-dependency check.

## Product boundaries

- Supports JavaScript and TypeScript repositories, with Jest, Vitest, and bun:test as the V1 frameworks.
- Findings target test files only; narrowly related production code is supporting evidence, not an independent finding target.
- E2E frameworks, automatic test rewriting, general source review, and languages outside JavaScript/TypeScript are out of scope.
- Discovery is repository-local and lexical. Generated/vendor/build paths, symlink escapes, and conservative E2E signals are excluded explicitly.
- A test file whose framework cannot be attributed is reported (`unsupported-framework` diagnostic, `totals.unsupportedFrameworkFiles`), never silently treated as zero tests — see "Current CLI" above.
- The audit pipeline is reporting-only: it never executes audited source, package scripts, test runners, or configuration modules. Read and parse diagnostics are emitted in JSON and do not fail the audit. This guarantee is bounded, not weakened, by Phase 7's benchmark execution (below): that execution runs only this repository's own Git-stored fixture corpus (`test/fixtures/corpus/`), from a dedicated adapter (`src/adapters/oracle-runner.ts`) reachable only from its own separate command (`src/cli/benchmark.ts`), never from `audit` under any flag — proven by a static import-graph test (`test/benchmark-cli-boundary.test.ts`), not by comment. Task P7-3's own benchmark database is likewise a separate SQLite file, opened only by `benchmark --store <path>` — its own `sqlite-benchmark-store.ts`/`benchmark-sample-port.ts` adapters are equally unreachable from `audit`, proven by the same closure test, and never share a file, a table, or a cache with the user's real audit store. Task P7-4's own new modules (`src/domain/benchmark-metrics.ts`, `src/adapters/benchmark-jsonl-writer.ts`) are equally unreachable from `audit`, proven by the same closure test extended with a third positive/negative control pair.
- Phases 2 and 3 emit structural test understanding and local evidence bundles only, with no network access. Phase 4 adds real Jev evaluation and classification, opt-in only via `--evaluate`. Phase 5 adds local SQLite persistence, content-addressed caching, adaptive scheduling with request/token budget observance, `--resume <runId>` to continue an interrupted run (all behind `--evaluate`), and a cache-aware `--dry-run` that reads (never writes) that same store (see "Audit store", "Content-addressed caching", "Adaptive scheduling and resilience", "Resume", and "Dry-run cost and call estimate" above). Phase 6 adds per-request latency, the versioned canonical JSON report, terminal progress during a run, and the self-contained offline `--html`/`--open` renderer (see "Canonical JSON report", "Progress during a run", and "Self-contained HTML report" above). Phase 7 adds the deterministic-benchmark fixture corpus and, as of task P7-2, an oracle runner that proves each corpus case's declared mutation by real, isolated, timeout-bounded execution against that corpus only; task P7-3 adds `benchmark --store <path>`, which additionally samples Jev's real verdict for each case (bypassing the audit cache entirely, never touching the user's audit store), persists the sample beside its oracle proof in its own SQLite database, and `benchmark --store <path> --baseline <runId> --candidate <runId>`, which compares two persisted runs by fixture identity — refusing outright, rather than silently comparing, when the two runs used different rubric or classification-policy versions. Task P7-4 adds `benchmark --store <path> --metrics <runId>[,<runId>...]`, which loads one or more persisted runs and prints precision, recall, false-positive rate, needs-review routing, probability calibration, run-to-run stability, cost, and latency, one figure per rubric dimension, counting only proven cases — every rate is a fraction that carries its own count, and a dimension with no proven case reports that plainly rather than as zero — plus `--jsonl <path>`, which exports every loaded case outcome as newline-delimited JSON behind that explicit path, mirroring how `--html <path>` gates writing a report file (see "Deterministic evaluation" in `docs/technical-design.md`). Precision, recall, false-positive rate, needs-review routing, and calibration are counted over DISTINCT proven cases, never repeated-measurement samples (a stability run resampling the same 11 cases up to five times); cost, latency, and stability stay counted over samples, since repetition is genuinely what those three measure — see "Deterministic evaluation" for the fix and its justification.
- CI is reporting-only in V1; findings do not fail a build.
- Normal operation is autonomous and does not require human-in-the-loop labeling or approval.
